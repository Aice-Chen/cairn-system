# 记忆：价值边界、语义与更新

本文说明 Cairn 长期记忆的设计：各组成部分分别承担什么独特价值、如何避免内容同质化与重复双写、四种内容语义与行动效力、读写与淘汰重选规则、双链与基于 git 历史的时间信息，以及跨对话的更新与延续机制。文件目录与具体语法见[数据仓库](../components/data-repo.md)，读写工具与服务端规则见[服务端](../components/server.md)。

## 记忆的范围与组成部分的价值边界

记忆是系统保存的、与这位学习者个人有关的信息，以纯文本保存在学习者私有的 git 数据仓库中。学习材料（`sources/`）、通用学科知识以及学习者产出的代码或笔记作品均不属于记忆。

为避免“记录与掌握状态重复抄写”以及“学习特征与具体知识点混淆”，记忆的五个子部分按**回答的问题、组织维度与生命周期**明确切分职责：

| 组成部分 | 回答的核心问题 | 组织单位与生命周期 | 独特价值（为何不可互相替代） |
|---|---|---|---|
| **学习者设定**（`settings/`） | 学习者是谁，希望达成什么目标，约定了怎样的协作方式？ | 通用一页 + 每个项目一页；仅经学习者确认后更新 | 保存当前有效的个人目标、使用条件与协作指令，提供跨对话一致的权限与偏好前提 |
| **学习记录**（`records/`） | 过去的学习过程中具体发生了什么？ | 按日期归档的事件流，只追加不修改 | 保存压缩前的过程细节：单次尝试、卡点转折、获得的具体支持、决定变更经过。状态页随时间会被重写和裁剪，只有记录能用于事后核对依据或回溯演变轨迹 |
| **掌握状态**（`state/mastery/`） | 在某项领域概念、机制或能力上，目前处于什么水平？ | 按**可复用的概念、机制或能力**建页；随新证据合成并覆盖旧结论 | 跨项目复用的“当前能力快照”。新对话无需重读历史流水账即可获知最新能力边界；多次观察后只保留合成后的当前认识与关键依据锚点，不堆砌历次过程 |
| **学习特征**（`state/traits/`） | 面对新内容时，这位学习者怎么切入更有效、常在哪里出现偏差？ | 按**跨内容可迁移的认知与协作模式**建页；随跨场景观察持续验证修正 | 与具体学科内容解耦。`mastery/` 关心“是否掌握注意力机制”，`traits/` 关心“接触复杂系统时先追踪单条请求链路是否比先看静态模块图更易建立直觉”。它为新项目提供初始辅导假设 |
| **学习进度**（`state/progress/`） | 当前项目停在哪里、排除了哪些弯路、下一步怎么接？ | 每个学习项目一页；随阶段推进覆盖更新 | 维护单个项目的工作台现场：大纲进展、未决问题、已尝试但走不通的路径，以及已确定的下一步安排 |

当某个概念仅发生过第一次交互时，`records/` 中的单次事件与 `mastery/` 中的初始判断在信息上自然相近；随着后续交互增多，两者迅速分化：`records/` 继续按时间留存每次具体事件，而 `mastery/` 用最新证据合并、修正并覆盖已被超越的旧快照，保持页面简明。

## 内容的语义与行动效力

### 四种内容语义

记忆中的文字按实际含义与来源分为四种，其解释方式不因所在目录而混淆：

| 语义 | 含义 | 示例 | 在辅导中的效力与用法 |
|---|---|---|---|
| **决定与约定** | 学习者作出的选择：目标、使用条件、投入上限、协作规则、选定的下一步 | “本项目核心模块先由我自己写，卡住时只提示方向” | 在适用范围、期限与成立条件内约束教学安排 |
| **自述** | 学习者对自身经历、已有基础、把握度或感受的陈述 | “以前写过 Go 并发，但没接触过 GPU 编程” | 了解起点的个人背景信号；随实际表现补充核实，不作为行动指令 |
| **观察** | 具体条件下实际发生的尝试、回应、错误、修正与事件 | “2026-11-14 在提示检查最后两维形状后，自行修正了掩码广播错误” | 形成判断的事实依据；保留当时的支持条件与信息来源（直接观察或事后自述） |
| **推断** | 模型基于有限观察归纳出的当前认识：能力边界、卡点原因、特征假设 | “能无提示说明缩放因子原理；实现多维广播时仍需形状检查提示” | 当前最佳工作认识；写明依据范围，随新证据出现随时修订 |

### 行动效力与决定的自然边界

**行动上的约束力只来自学习者的决定。** 其余内容（模型的推断、学习者的背景自述、以及上一轮对话留下的未完工作现场）均为供当前模型开展判断的参考信息。

关于学习者决定的成立与有效期，明确三点边界：
1. **写入者不等于决定者**：模型可以将学习者在对话中明确作出的选择写入设定或进度，其效力来自学习者的表态；模型自行构想的做法即便写下，也不具备约束力。
2. **范围、期限与自然终结**：决定在其对应的范围与条件内有效。跨项目约定放入通用设定，单项目约定放入项目设定；带期限的安排（如“考前一周采用闭卷推导”）到期自然结束；一次性接续决定（如“下次先练一下张量变形”）在执行完毕后自动转为已发生的历史进度，不再持续约束后续对话。
3. **防止跨对话的议程锚定（进度页不设模型候选建议栏）**：如果进度页固定要求模型写下“后续候选建议”，写入端容易每次凑出额外的练习提议，读取端的新模型又容易将其当作默认议程顺延执行。因此，进度页的接续部分只记录**“学习者已确定的下一步决定”**与**“客观的当前停留现场（做到哪一步、有哪些未决问题与已排除路径）”**。模型单方面想到的拓展或巩固点子不预先写入进度页锚定下次对话（能力的支持局限本就记在 `mastery/` 中，下次模型可结合当时的请求实时判断；仅当学习者明确表示“把这条建议先记下来备忘”时才予保留）。

## 写入、归属、淘汰重选与读取规则

模型在写入学习记录、更新状态页面、编写 `summary` 摘要及读取记忆时，统一遵循以下五条规则：

**1. 保持来源、范围和效力。**  
推断经过概括或转述仍是推断，带有支持条件的表现压缩进 200 字 `summary` 时仍须保留关键条件（如“在形状提示下完成”不能压缩成“已能独立实现”）。多次引用同一历史观察时，其证据强度仍只对应那一次观察。

**2. 严格区分学习者产出与模型顺势补全（如实归属）。**  
辅导交流中，当学习者给出模糊、跳跃或仅对了一半的回答，而模型顺着话头替其补全了关键推理链条时，记录与掌握状态只把**学习者自己明确说出或独立完成的部分**计入其能力表现；模型补全的逻辑环节如实记作本次的“支持条件”，防止代为补全的内容混淆长期能力判断。

**3. 判断以已有依据为界，不列开放式的“待考察清单”。**  
一次表现未覆盖的保持、迁移或变式情境没有边界。掌握状态只陈述已有依据支持什么，以及与当前明确目标之间已观察到的具体差距（须注明对应目标），不写“尚待观察独立实现、延迟保持”之类的通用备忘，避免变相生成强制复习任务表。

**4. 更新状态与摘要时主动淘汰重选。**  
阶段性更新不是只往状态页末尾追加新段落。每次修订 `state/` 页面及其 `summary` 时，模型需结合当前仍有持续用途的信息重新整合：已被新表现超越的早期局部卡点予以覆盖或浓缩为一句背景，已解决的临时问题和已完成的单次安排从当前现场移除，使状态页始终反映最新、精炼的当前认识。

**5. 详略与后续决策价值相称。**  
简单进展或常规观察一行即可；只有涉及长期约定、反复出现的障碍或关键能力边界时，才展开必要的任务与支持细节。

以上规则可以用同一个标准检验：**脱离本次对话后，后续读者能否仅凭页面文字准确还原它当时指什么、依赖什么条件，并独立判断它在新的目标下是否仍然适用。**

## 三类记忆的组织细节

### 学习者设定（`settings/`）

设定保存学习者本人的陈述、目标与持续协作约定，按作用范围分为两级：
- **通用设定**（`settings/general.md`）：跨项目适用的个人背景、长期方向与通用辅导约定，每次 `start_session` 加载全文。
- **项目设定**（`settings/projects/<项目>.md`，可选）：特定学习项目的目标、使用条件、时间约束与专门约定，指定该项目时加载全文，其余项目仅返回名称与摘要。

更细的情境或时间条件直接用自然语言写在具体约定条目内，不再拆分更多目录层级。范围更具体的约定优先于宽泛约定；个人设定优先于插件指引的默认做法。设定的新建与修改必须经学习者明确表态或确认，由专用工具 `update_settings` 写入并记录确认说明。

### 学习状态（`state/`）

- **学习进度**（`state/progress/<项目>.md`）：记录项目材料路径、大纲或里程碑状态、当前停留的客观工作现场（含未决问题与已排除的失败尝试），以及学习者已确定的下一步安排。当新对话中学习者提出新的具体请求时，以当前请求为准；当学习者要求“接着上次继续”时，按已定安排与未完现场接续。
- **掌握状态**（`state/mastery/`）：页面优先按**可复用的概念、机制或能力**命名（如 `缩放点积注意力`、`内存合并访问`），避免按一次性任务命名（如“作业一第二题”），以便跨项目共享和关联。一个页面可包含围绕同一主题的多项判断（如原理理解与编码实现），每项写明当前能力边界、核心依据（日期、任务、支持条件、信息来源）及影响选择时的确信度说明。
- **学习特征**（`state/traits/`）：记录跨内容可检验的辅导工作假设，主要包括三类信息：（1）有效的认知切入与表征方式（如面对复杂系统先追踪单条数据流优于先看分层抽象）；（2）跨领域的典型执行习惯或盲区（如动手实现前易忽略张量形状或并发边界不变量）；（3）自我评估倾向（如听懂原理后易高估独立实现速度）。每条特征注明观察到的项目/任务范围与已知例外，保持精炼，避免泛化为无根据的性格标签。

### 学习记录（`records/`）

学习记录保存在 `records/YYYY-MM-DD.md` 中，按日期每天一个文件，每条记录由服务端写入时间、所属项目和可选的对话标记。按日期而非按对话分文件的原因有三点：一是每条记录都必然具备确定时间，而对话标记在部分客户端可能缺失或中途更替，记录落盘位置不应依赖不可靠的标记；二是单次对话可能跨越数周，按日期切分边界稳定；三是回查历史依据时主要按日期定位。

发现既有记录与事实不符时，通过 `add_record_entry` 追加一条更正说明（注明所更正条目的时间），并据此修订相应的学习状态页面，不删改历史记录原文。

## 页面、链接、索引与时间信息

**页面与粒度**：每个 `.md` 文件是一个页面，frontmatter 中包含必填的单行 `summary`（不超过 200 字符）。页面粒度由模型按三条实用标准把握：能用清晰的概念或主题名指称、能独立更新、能用一两句话概括；随内容演进可通过 `move_page` 重命名或通过 `remove_page` 合并拆分。

**双链 `[[页面名]]` 的定位**：双链只承担**语义关联与阅读导航**两项职责，与时间统计完全解耦：
1. 供服务端在 `start_session` 时从当前项目进度页提取直接关联的状态页摘要，以及供 `get_related_pages` 查找上下游关联页面；
2. 供学习者在 Obsidian 中直接点击双向跳转核对。模型漏写个别双链只影响局部跳转便利性，不会造成任何系统计时或状态错误。

**全量名称清单与跨项目关联**：服务端自动解析所有页面的 frontmatter 生成索引。为解决跨项目学习时的“概念孤岛”问题（例如在 `vllm` 项目中自动识别并复用此前在 `cs336` 中建立的 `[[缩放点积注意力]]` 页面，防止因看不见旧页面名而重复创建同义的 `[[注意力计算]]`），`start_session` 除了返回当前直接关联页面的完整摘要外，还会返回**其余全部学习状态页面的轻量名称清单（含最近更新日期）**。个人数年积累的主题级页面通常在数百页以内，名称清单开销极小，却能让模型在开场时即掌握完整的个人知识目录，按需调用 `read_pages` 查阅详情并准确使用既有名称建立链接。

**基于 git 提交历史的时间信息**：服务端不再通过解析 `records/` 中的双链来计算页面时间，也不单独维护脱离数据仓库的工具调用数据库，而是直接从每个学习状态页面文件自身的 **git 提交历史（启用重命名追踪）** 计算三项确定信息：
- **首次创建日期**：该页面首次提交建立的日期；
- **最近更新日期**：该页面最近一次发生内容更新提交的日期；
- **累计更新天数**：该页面发生过提交更新的不同日期总数。

这样设计的理由有两点：第一，数据仓库本身就是纯文本 git 仓库，多端同步时 git 历史天然随仓库完整迁移，无额外状态同步负担，也不会因模型在 `records/` 中漏打双链或后台调用 `read_pages` 查阅而污染时间；第二，从教学意义看，如果某次对话只是顺口提及某个旧词而未作实质检验，本就不应刷新其间隔时间；反之，若经过间隔再次检验或在新情境中成功运用，模型在阶段更新时修订该页依据与确信度，页面 git 更新时间便随之自然刷新。

## 记录时机、阶段性更新与跨对话延续

系统不记录对话的开始与结束，任何流程都不依赖无法可靠捕获的“会话关闭”事件。

**按观察闭环与阶段节点写入（兼顾教学表现与跨端体验）**：  
在日常多轮讲解与探讨过程中，模型不需要每两三轮机械调用写入工具，以免在思路尚未充分展开时过早给表现定性，同时也减少网页端远程 MCP 可能出现的写操作确认打断。写入按两类时机进行：
- **学习者的明确决定或目标变更**：一旦确认，当场调用记录或设定工具落盘，避免遗漏；
- **学习表现与状态修订**：待一个局部观察闭环完整（如一次问题分析、尝试与修正走完）或进入自然阶段停顿（主题切换、阶段小结、学习者准备离开）时，调用 `add_record_entry` 记录本段有价值的事件，并同步调用 `write_page` / `edit_page` 更新涉及的进度、掌握状态和学习特征页面。

**同步提交与异步远端推送**：  
服务端串行执行写入并立即完成本地 git 提交后即返回工具结果；若配置了远端仓库，`git push` 在后台异步执行（推送异常在下一次工具返回中告知）。这一机制对远程 HTTP 服务端（供 ChatGPT 网页端、Claude 网页与移动端连接）和本地 stdio 服务端（供 Claude Code、Codex 连接）同样适用，消除了每次写入的网络阻塞。在支持插件钩子（Hooks）的本地客户端中，还可利用上下文压缩前或停止类钩子提醒模型补齐尚未落盘的阶段记录，作为可选增强。

**未整理记录的确定性断点检测**：  
若一次对话在写入了若干条 `records/` 后意外中断、未能完成阶段性状态更新，服务端无需依赖双链比对，只需直接对比**学习记录的最新条目时间**与 **`state/` 目录（或该项目状态）的最近提交时间**。若存在晚于最近一次状态更新的新增记录，下次 `start_session` 会直接将这批未整理记录标出，供新对话的模型核对并补入相应状态页。

**并发写入与学习者直接编辑**：  
服务端无会话级内存状态。多窗口并发写入时，`records/` 只追加，`state/` 通过读取时返回的版本标识（`base_version`）做乐观并发校验，`settings/` 须附确认说明。学习者在本地直接用编辑器或 Obsidian 修改页面后，服务端在下次 `start_session` 中提示最近被人工直接编辑过的页面；模型按修改内容的语义（修改设定视为新决定，补充经历视为自述，修正判断结合依据核对）自然吸纳。
