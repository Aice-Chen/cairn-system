## 4. 下一步：5.2 版本、迁移与 git 的角色

**待讨论的问题（按讨论记录中已有的线索整理，仅作起点）：**

1. **三个版本的关系：**插件（技能文本）、服务端、数据格式（FORMAT_VERSION）。学习者的立场是：插件升级后其他部分整套随之升级，不考虑新旧插件混用，只需保证数据的兼容和迁移（D1）。可考虑插件与服务端同版本发布，数据格式单独编号；开场时核对插件与服务端版本是否一致，不一致时提示更新插件。
2. **迁移的执行：**原始数据（记录、设定）格式稳定，改动时需迁移；状态可由证据重新评估生成（D7，推断可以重放）；派生数据随时重建。需要决定迁移脚本放在哪里、何时运行、失败怎样回滚、怎样验证。
3. **git 的角色：**历史记录、与学习者本地的同步、备份；每次沉淀对应一次提交（5.1-5）；证据追加的提交合并进行。需要明确：git 历史是否同时作为状态版本的依据，还是状态版本记录（1.10）独立存在。
4. **版本管理（暂缓区中的问题）：**回退较早的沉淀时，如果之后的沉淀改动过同一条目，会产生冲突。已列出的可选做法：只允许回退最近一次；依次撤回之后改动过同一条目的沉淀；回退后用剩余证据重新评估相关条目。
5. **首次迁移：**把当前已部署的数据迁移到新结构，包括把 profile/10-learner.md 中的背景移入状态、concepts.md 拆成每个条目一个文件等。现有数据很少，是迁移成本最低的时候。
6. **数据仓库的目录布局：**5.1 定了各类数据的形态，具体的目录结构尚未写出。

## 6. 讨论方式的约定

学习者明确提出过、或在讨论中形成的做法：

- **先讲清问题和原因，再给方案；先讨论，再决定。**学习者会逐条审查思路，所以每个决定都要写明它要解决什么、为什么这样选、代价是什么。
- **回复保持详细。**学习者偏好充分展开的篇幅，太简略会看不清思路。
- **不要预先防御、预先否定。**只在很可能产生误解时才澄清"不是什么"。
- **结尾先回顾整体问题，**再提出是继续当前子问题，还是回到上一级。
- **每轮末尾列出需要学习者确认的点。**
- **讨论记录的维护：**未经确认的内容不写入；每完成一个议题统一更新记录和项目记忆；核对文件时只输出简短的结果；文档和工程中使用术语表中的正式术语，讨论中可以用口语解释。
- **常见的错误，下次注意：**
  - 不要把需要语义理解的工作交给服务端（服务端只能处理结构、时间、数量、名称匹配）；
  - 不要把模型的推断（描述）和学习者的指令混在一起；
  - 不要在一个概念上叠加两种用途（例如"提议"曾同时指两类待确认事项）；
  - 提出新规则时，检查它是否与已定结论冲突，冲突时明确指出并说明取舍。

## 7. 最关键的十条原则（细节见讨论记录）

1. 约束输入的完整性，放开判断的方式；约束记录的可追溯性，放开记录的写法（0.4）。
2. 指导按约束力分为硬约束、约定、目标、启发；启发不具约束力（0.4）。
3. 证据是发生过的事实，不可修改；状态由证据沉淀而成，可以修正（0.2-1）。
4. 状态由主张组成，每条主张说明依据类型、时间、置信程度、证据位置（0.3）。
5. 学习者设定是指令，模型遵守；学习者状态是描述，模型权衡（议题 2）。
6. 推断有增量更新和重新评估两种方式；"已沉淀"的标记只约束增量更新（1.4-8、1.6-11）。
7. 每次沉淀只针对一个会话的证据；回顾是跨会话的重新评估（1.6-5、1.6-6）。
8. 服务端只理解结构，不理解语义。
9. 推断可以重放；以试跑检验推断（D7、D8）。
10. 基线是 MCP 加技能，钩子和子代理只作增强（D4）。

## 9. 一次需要记住的事故

讨论中曾有一轮回复因用量上限被中断：中断前已写入了讨论记录和项目记忆，回复却没有发出，而且写入的内容把一个尚未确认的提议当作了定论。下一轮发现后已撤回。这正是 1.6 中"放弃的对话分支留下了副作用"的情况，也是"未经确认的内容不写入记录"这条约定的由来。新会话中如果发现讨论记录与对话中的结论不一致，先向学习者说明，再处理。
