# Cairn 重构讨论记录（2026-10）

本文件记录以插件为主的重构讨论，是后续设计和开发的依据。每完成一个议题更新一次；讨论全部结束后，结论并入 DESIGN.md，本文件作为历史记录保留在 `docs/design/` 下。

本文件是写给开发者的设计记录，完整保留推理和依据。技能中交给模型的说明是另一回事：它会按 0.4 的要求精简，只保留模型需要的部分，在议题 6 中撰写。

## 0. 结论索引

新会话先读本节，需要细节时再读对应章节。编号前缀即章节：D 为第 2 节；0.x 为议题 0；1.x 为议题 1；2-x 为议题 2；3-x 为议题 3；5.1-x、5.2-x 为议题 5。0.1 与 0.4 没有编号表，要点如下：
- **0.1** 术语分三层：学习过程模型、学习者状态模型、实现。
- **0.4** 约束按约束力分为硬约束、约定、目标、启发四层；总原则"约束输入的完整性，放开判断的方式；约束记录的可追溯性，放开记录的写法"；可追溯和标注来源为硬性要求；判断层次用 C1 到 C6 六个问题；启发层不具约束力，写明"不限于此"、写成思考工具、保持精简。

- **D1** 只保留插件形式，不保留无插件的退路。删除 `include_guide` 和 read_standard，格式规范改为技能的参考文件。插件升级时只需考虑数据的兼容和迁移
- **D2** 服务端可以理解数据的结构和内容，但架构必须具备兼容性和可迁移性；数据的组织方式会随使用而演进
- **D3** ChatGPT 的写入可以设为始终允许，写工具的粒度不受确认次数的限制
- **D4** 基线是 MCP 加技能，覆盖两个网页端；钩子和子代理只作为增强。能力判断依据可观察的信号（工具列表、钩子注入内容中的标记），优先采用幂等的设计，以减少分支
- **D5** 知识掌握（原称 concepts）暂时维持完整送入模型，视为针对性讲解的核心；规模问题在议题 1.5 讨论（3-B 修订：知识地图始终完整，详情在预算内送入，见 3-9）
- **D6** 资源平铺：sources/ 第一层就是资源，分类用命名前缀表达，不用文件夹
- **D7** 推断可以重放：证据是不可修改的原始数据，状态由它派生；改进推断方法后，可以对全部证据重新沉淀，重新生成状态
- **D8** 以试跑检验推断：预先定义推断出错时的表现（置信程度虚高、结论被来回改写、旧结论长期不被检验、简单内容被反复检验），定期检查，针对性地改进技能中的说明（5.2 补充：观察项增加登记的条目后来被合并的比例、标注更正的次数）
- **0.2-1** 区分状态与证据：证据是发生过的事实，不可修改；状态由证据沉淀而成，可以修正；推断属于状态，并标明来源
- **0.2-2** 证据分为自述、测评、自然表现三类；复述按由谁发起来归类；"保持"需要间隔才能观察到
- **0.2-3** 核心循环：加载 → 互动 → 记录 → 沉淀；会话内依靠上下文即时调整，不需要每轮重新注入状态
- **0.2-4** 各种场景是同一循环中不同的互动活动
- **0.2-5** 证据由模型判断，值得记录就当即记录，必要时每轮都可以记。每个会话的证据记在一个文件中（原称 log），只追加；不变量改为"已记录的证据不再修改"。记录的单位是一条条证据：事实、证据类型、涉及的概念、情境（包括疲惫、赶时间这类临时状态，它们影响证据的诊断性）、时间，以及可选的、标为推断的当场理解。是否值得记录，由目标引导：它会不会改变或印证对学习者状态的认识，以后的模型是否需要知道它
- **0.2-6** 沉淀自动进行，不需要学习者提出；下次加载时补做未完成的沉淀（幂等）；沉淀后给出简报。agent 客户端可以用会话结束的钩子提前沉淀
- **0.2-7** 重大变更由服务端设为"待确认"，确认前不生效，每次加载时列出未处理的待确认事项；是否重大由模型判断；模型在回复中询问学习者，有结构化提问工具的客户端可以用它作为增强
- **0.2-8** progress 自动更新且对学习者可见：开场一句话交代位置，简报中列出变化，随时可以查看和调整；较大的调整（跳过某一讲、修改截止日期）需要确认
- **0.3-1** 状态包括背景、目标、偏好、学习特征（学习方式上的特点，含自评准确度）、知识掌握、进度与待续事项、待确认事项（1.9 修订：取消"疑问"；议题 2 补充：待确认事项分为待确认的状态变更和设定建议；实现中各方面的归属与存放见 2-5、5.2-24）
- **0.3-2** 推断出的缺口和待确认之处都并入知识掌握，不另设一类
- **0.3-3** 各方面由不同的一方说了算，见上表
- **0.3-4** 每条陈述必须能回答依据类型、时间、把握程度、证据位置四个问题，写法自由
- **0.3-5** 临时状态、与学习无关的个人信息、原始证据不放进状态；临时状态作为证据的情境记录
- **0.3-6** 模型可以改写关于学习者的内容，但不能在学习者不知情的情况下改写；会改变模型行为的修改须由学习者提出或确认（议题 2 修订）
- **0.3-7** 状态由主张组成，每条主张有范围和权威（1.4 讨论中补充）
- **0.5-1** 业务模型由领域知识、学习者状态模型、证据模型、引出模型、教学、学习过程模型组成，结构借用 ECD 和 ITS
- **0.5-2** 领域知识由大模型和学习材料承担，不保存
- **0.5-3** 互动同时具有学习价值和信息价值，引出证据时优先选择两者兼具的方式
- **1.2-1** 条目由名称和别名、摘要、详情三部分组成，由模型维护；摘要是约定，详情只写明目标
- **1.2-2** 证据索引由服务端计算，模型不再手工维护；前提是证据的概念标注可靠，这条约定因此更为重要
- **1.2-3** 推断出的缺口使用同一种结构，摘要中写明"很可能未掌握"及其来源
- **1.2-4** 暂不设置机器可读的状态等级；需要时（间隔复习、规划筛选、知识地图压缩）从摘要中提取，作为一次数据迁移
- **1.3-1** 粒度以"教学决策是否不同"为标准，先粗后细、按证据拆分，平铺不存层级
- **1.3-2** 技能和操作也作为知识掌握条目
- **1.3-3** 正式名称加别名，取消复合名称；服务端解析别名；命名修正只通过别名进行。未知标注改为在写入证据时拦下，新概念须明确声明（1.10 修订）
- **1.3-4** 改名、合并、拆分由模型在沉淀时执行，在简报中告知，不需要确认
- **1.4-1** 推断发生在会话中、沉淀时、使用时三个时刻
- **1.4-2** 以主张、范围、权威、诊断性、置信程度、时效、信息价值七个概念为核心建立统一的推断框架；推断由五个操作组成，作为启发提供给模型
- **1.4-3** 各方面的推断使用同一框架，差别只在范围和权威；学习特征的原则是框架的推论
- **1.4-4** 推断的指导按约束力分属四层，见上表
- **1.4-5** 证据索引增加各类证据的数量和首次证据时间
- **1.4-6** 遗忘在使用时考虑；冷启动多观察是信息价值的自然结果
- **1.4-7** 推断可以重放（D7），以试跑检验推断（D8）
- **1.4-8** 区分增量更新与重新评估；增量更新中历史证据只用于理解，不重复计入（1.10 讨论中补充）
- **1.5-1** 现阶段维持 D5，整份送入（3-B 修订：见 3-9）
- **1.5-2** 摘要增加跨主题的个人化关联，以及待验证之处和已知误解的提示（修订 1.2）
- **1.5-3** 详情按"是否仍影响当前判断"保留经过，已被取代的压缩为一句，完整历史在证据中；相应修订 1.4 中关于矛盾的约定
- **1.5-4** 体积监控只在后端进行，不进入模型可见的流程
- **1.5-5** 规模增长后的送入策略暂不决定，记入暂缓区；送入方式只影响服务端组装开场内容，不改变数据结构，以后调整不需要迁移（5.2-C：方向定为常驻知识地图、详情按需读取，见 5.2-33）
- **1.6-1** 加载时给出未沉淀的情况，并送入未沉淀的证据本身（3-B：有预算，超出时给出条数和最近的若干条，补做沉淀列为首要事项）
- **1.6-2** 沉淀进度按单条证据记录
- **1.6-3** 沉淀的时机：学习者的结束信号、段落结束时模型自动进行、下次加载时补做；不用会话结束的钩子
- **1.6-4** 会话标记由服务端发放、模型原样带上，其余追踪全部由服务端完成（3-C：短形式，放在每次工具结果末尾的状态行中，见 3-18）
- **1.6-5** 每次沉淀只针对一个会话的证据；本会话用本会话的证据和上下文；闲置超过阈值的会话由新会话代为沉淀，单独提交；学习者可随时干预
- **1.6-6** 日常沉淀与回顾两种；回顾跨会话，由服务端的事实性指标与模型提出的理由共同触发，在学习结束后进行，agent 客户端交给子代理（5.2 修订：服务端指标"未处理的未知标注数"改为"上次回顾以来新登记的条目数"）
- **1.6-7** 按条目写入，一次沉淀整体提交，幂等，基于最新版本
- **1.6-8** 回退沉淀与撤销证据是两个独立的操作；回退使证据变回未沉淀；由学习者发起（5.2 细化：回退有前提，不满足时改为重新评估）
- **1.6-9** 状态带修订号（5.2 前称"状态版本"），服务端按会话追踪已知的修订，变化以增量随工具结果告知（3-C 修订：设定的变化立即附全文，其他变化只标记数量、按需获取，见 3-19）
- **1.6-10** 简报以服务端计算的提交前后差异为依据
- **1.6-11** "已沉淀"的标记只约束增量更新；回顾是跨会话、长时间跨度的重新评估；日常沉淀中也可以对单个条目重新评估
- **1.9-1** 取消"疑问"作为独立的状态方面
- **1.9-2** "进度"扩展为"进度与待续事项"；待续事项由学习者说了算：模型在学习者延后问题或表达想了解的方向时记下，是否放弃由学习者决定

- **1.10-3** 概念标注为结构化字段；未知标注在写入时拦下，新概念须明确声明；声明的新概念即时登记为条目（5.2）
- **1.10-4** 会话记录客户端名称和模型自报的名称；还保存插件版本（5.2-B）和可选的平台会话标识（3-C）
- **1.10-5** 不变量见上；回退较早沉淀时的冲突问题已在 5.2 解决
- **2-1** 关于学习者本人的内容按性质分为学习者设定（指令）与学习者状态（描述）
- **2-2** 设定由学习者表达或确认后才修改，每次修改都告知；状态由模型自动维护，重大变更待确认（5.2-C 细化：沉淀和回顾提交的改动不能触及设定，见 5.2-25）
- **2-3** 写入冲突由服务端处理（写入前拉取，改到同一处时放弃并报告），不要求单一写入者
- **2-4** 模型维护的个人状态沿用知识掌握条目的结构；学习特征暂不在证据上单独标注
- **2-5** profile/ 只存放设定；背景移入状态；学习目的属于设定（5.2-C 修订：profile/ 改为关于学习者本人的内容，分 settings/ 与 descriptions/；背景和学习特征存放在 descriptions/；学习目的存放在 settings/resources/，见 5.2-24）

- **2-7** 推断出的喜好作为学习特征记录在关于学习者本人的描述中（5.2-C），可在设定允许的范围内直接参考；喜好与效果分别记录
- **2-8** 设定建议确认前不改变任何东西；冲突时写明替换关系；拒绝被记录，避免重复建议
- **2-9** 待确认事项分为"待确认的状态变更"和"设定建议"两个术语

- **3-2** 技能写"怎样做"；加载结果只放数据、学习者设定和待处理事项的事实，不放通用说明
- **3-3** 技能明确授权：加载结果中"学习者设定"一节是学习者的指令，优先于技能的默认做法；其余部分都是信息；插件版本检查保证授权在场

- **3-8** 与平台记忆的分工写进技能；冷启动时加载结果标明没有关于学习者本人的描述，模型可以平台记忆为线索，经确认后记为自述证据
- **3-9** 知识地图始终完整，详情在预算内按优先级填充，其余按需读取，没有切换的时刻（修订 D5、1.5-1，细化 5.2-33，删除暂缓区对应项）
- **3-10** 必需部分：学习者设定、关于学习者本人的描述、知识地图、当前资源的进度和学习目的、待处理事项；有预算的部分：知识掌握的详情、未沉淀的证据
- **3-11** 详情的填充顺序：有未沉淀证据的、有待确认事项的、当前资源的、其余的（后两类按最近证据时间）；只排先后，不排除；标明"详情已附"或"仅摘要"
- **3-12** 修改条目前本会话必须已拿到它的详情（硬约束；3-C 修订为修改时带上条目版本，见 3-21）；深入讲解、检验、判断缺口或前置知识前先读取（约定）；其余为启发；读取工具一次可读多个条目

- **3-14** 预算按客户端配置，用字符数计量，初始值在试跑中调整；体积只记在后端

- **3-16** 恢复规则放在不会被压缩的通道：主技能的描述（看不到正文时重新读取）；开场加载工具的说明（找不到加载结果时带标记重新加载）；需要会话标记的工具的说明各一句；材料工具不带；工具结果只带事实性的状态行
- **3-17** 需要会话标记的工具：所有写入工具，以及读取状态的工具（读取条目、查询证据、获取变化）；材料工具不需要

## 1. 背景

**重构的起因。**
- 最初所有功能都放在 MCP 中，start_session 一个工具承担了加载说明、返回状态、扫描材料等多项职责。
- 协作说明通过工具结果送达。模型对工具结果中的指令天然更谨慎，而且工具结果在上下文压缩时容易丢失。
- 因此决定改为以插件为主：MCP、技能、钩子、子代理，同时适配 Claude 和 ChatGPT/Codex。

**平台现状（2026-10 查证）。**
- **Claude：**插件可以包含技能、命令、连接器、子代理和钩子，保存在账号中，网页、桌面、手机通用。在聊天中只能使用技能、命令和连接器，钩子和子代理只在 Cowork 和 Claude Code 中运行。
- **OpenAI：**ChatGPT 和 Codex 共用插件目录。插件可以包含技能、MCP 和钩子，钩子只在 Codex 运行时中执行（Codex 本地、ChatGPT 桌面端 Work），在网页上安装插件不会部署钩子脚本。OpenAI 接受 Claude 兼容的插件清单。
- **两个网页端都没有钩子。**已确认 ChatGPT 网页端可以使用个人插件中的技能。

## 3. 议题 0：业务模型与建模原则

### 0.1 术语（已定）

| 层次 | 回答的问题 | 举例 |
|---|---|---|
| 学习过程模型 | 学习怎样进行，系统在其中做什么 | 证据从哪里来，怎样沉淀，怎样使用 |
| 学习者状态模型 | 理论上应该描述学习者的哪些方面 | 背景、目标、偏好、掌握情况、学习特征、进度与待续事项，以及每一项的置信程度 |
| 实现 | 存在哪里、怎么读写 | profile/（settings/、descriptions/）、state/（concepts/、progress/）、records/，以及各个工具（5.2-C） |

前两层是业务模型，第三层是它的落地。讨论按"先业务模型、后实现"的顺序进行。

### 0.4 约束的边界（已定，1.4 讨论中重构）

**要解决的问题。**约束过多，模型会为了满足格式而改变行为，粗糙的规则会替代更好的判断；约束过少，不同模型（Claude、GPT 以及它们未来的版本）在长时间跨度里读写同一份记录，会互相看不懂，服务端依赖的结构也会失效。掌握程度没有公认的衡量标准，用规则替代判断，通常比让模型自己判断更差。

**重构的原因。**初版分为硬约束、约定、目的、示例四层，其中前三层按约束力划分，"示例"却按内容的形式划分。两种依据混在一起，"参考因素"放进"目的"层就会变成模型必须完成的事。重构后只按约束力分层。

**四个层次（按约束力）。**

| 层次 | 约束力 | 内容 | 例子 |
|---|---|---|---|
| 硬约束 | 系统强制，模型无法违反 | 存储和检索的结构、写入时机、不可篡改、可追溯、标注来源 | 证据不可修改；证据索引由服务端计算 |
| 约定 | 模型必须遵守，为了跨会话、跨模型的一致 | 命名、标注、记录的基本规范 | 没有新证据不改结论；由学习者说了算的方面，推断只能作为设定建议提出 |
| 目标 | 模型要达成，怎么达成由它决定 | 每份记录、每个判断要服务的目的 | 置信程度与实际相称；状态服务于教学决策 |
| 启发 | 不具约束力，模型可以参考、补充，有更好的理由时也可以不用 | 思考框架、参考因素、示例 | 影响诊断性的因素；推断的五个操作；各处的示意 |

**启发层的写法要求。**即使不具约束力，列出来的内容也可能吸引模型的注意力，让它只盯着列表中的几项，形成隐性的约束。因此：
1. 明确声明不具约束力，例如"可以参考以下方面，不限于此"。
2. 写成思考的工具，而不是检查清单：给出原理和几个例子，不要求逐项核对。
3. 保持精简。

**判断一项内容放在哪一层的六个问题。**

| 问题 | 回答为"是"时 |
|---|---|
| C1 服务端的逻辑依赖它吗 | 需要硬约束 |
| C2 不同会话、不同模型之间需要一致吗 | 需要约定 |
| C3 试跑中出现过它能解决的具体问题吗 | 有依据，可以加 |
| C4 它会改变模型的教学或判断行为吗 | 避免，或改写为目标 |
| C5 这件事有公认的标准吗 | 没有的话交给模型判断，但要求写出依据和置信程度 |
| C6 它的作用是帮助判断，还是规定结果 | 帮助判断的放在启发层；规定结果的，再按 C1 到 C5 决定层次 |

**总原则：**约束输入的完整性，放开判断的方式；约束记录的可追溯性，放开记录的写法。

**两条硬性要求。**
- **可追溯：**每一个结论都能找到支撑它的证据和日期。
- **标注来源：**关于学习者的每一条信息都标明来源（自述、测评、自然表现，或推断）。

**按此边界检视原有设计**（具体修改在议题 1、6 中进行）：

| 原有内容 | 应属的层次 | 方向 |
|---|---|---|
| log 文件名、写入后不可修改 | 硬约束 | 保留；不可修改的对象改为"已记录的证据"，见 0.2 |
| `[[ ]]` 标注概念 | 约定 | 保留 |
| 观察与结论分开 | 约定 | 保留 |
| 证据类型标注 | 约定 | 保留"标注来源"的要求，类型清单按 0.2 的三类 |
| log 的四节结构 | 原为约定 | 改为说明目标，几节结构作为启发 |
| concepts 的"最近观察""学习来源""相关记录" | 硬约束 | 改由服务端计算，见 1.2 |
| concepts 的"掌握情况""待确认" | 目标 | 自由描述，只写明用途 |
| "对他有效的类比" | 不合格（C4） | 删除，并入学习特征，由模型自由描述 |
| "名单里没有就是缺口" | 不合格（C5） | 删除，由模型综合背景、诊断和证据判断 |
| "待观察"标记 | 硬性要求的一部分 | 保留"必须表达置信程度"，表达方式不固定 |
| 讲解与检验的原则 | 目标加启发 | 基本符合，议题 6 中再审视 |

**增加约束的流程。**第一版尽量精简。只有当试跑中观察到具体问题（C3），且约束能针对性地解决、又不扭曲模型行为（C4）时，才增加约束。问题的来源有两个：定期查看不同模型写下的记录，以及学习者在偏好中记下的反馈。

### 0.2 学习过程模型（已定）

**状态与证据。**

| | 状态 | 证据 |
|---|---|---|
| 是什么 | 系统对学习者的认识 | 互动中实际发生的事 |
| 怎么来 | 由证据沉淀而成 | 在互动中产生 |
| 存在哪 | 持久保存，会话开始时加载 | 先记入证据记录，再被沉淀 |
| 能否修正 | 能 | 不能 |

推断是模型依据证据和世界知识得出的结论，归入状态，并标明来源为推断。外部事实（材料、大纲、截止日期）不是关于学习者的信息，但属于会话的背景。

**证据的三种类型（按产生方式分）。**

| 类型 | 定义 | 例子 | 能揭示什么 | 局限 |
|---|---|---|---|---|
| 自述 | 学习者对自己的陈述 | 背景、自评、"这里我懂了"、对讲解方式的反馈 | 目标、偏好、自我认知 | 可能高估或低估 |
| 测评 | 学习者对模型有意设计的任务的完成情况 | 诊断题、练习、要求复述、预测输出、找错 | 能否在指定任务上做到 | 只覆盖被测到的点；当场答对可能只是短期记忆 |
| 自然表现 | 学习者自发的行为和产出 | 主动提问（内容、深度、前提中的误解）、主动解释、做题思路、作业代码和提交历史、卡住的位置和反应 | 真实的理解边界、好奇的方向、误解、前置缺口 | 不受控、零散，需要多次积累 |

复述按由谁发起来归类：模型要求的属于测评，学习者主动的属于自然表现。"保持"（隔一段时间是否还记得）只有在间隔之后再次出现证据才能看到，所以时间也是证据的一个维度。

**核心循环。**

```
① 加载：状态和必要的信息进入上下文（会话开始时；上下文压缩之后）
② 互动：使用状态进行讲解、检验、练习……，其中不断产生证据，模型据此当场调整
        （会话内的小循环：互动 ⇄ 证据，依靠上下文完成，不需要每轮重新注入状态）
③ 记录：写入证据
④ 沉淀：由证据更新状态，自动进行；给出简报，重大变更等待确认
   → 持久保存的状态 → 回到 ①
```

**场景是同一个循环中不同的互动活动。**

| 场景 | 何时发生 | 加载的重点 | 互动活动 | 主要证据 | 额外产出 |
|---|---|---|---|---|---|
| 冷启动 | 刚开始使用，或进入全新的领域 | 少量学习者设定和自述，几乎没有其他状态 | 诊断：自评加快速验证 | 自述、测评 | 初始状态，标明来源 |
| 接入资源 | 加入或更新资源 | 现有状态、材料 | 建立或更新进度，必要时诊断前置知识 | 测评 | progress |
| 常规学习 | 大多数会话 | 状态、当前资源的进度、相关材料 | 讲解、检验、练习 | 三类都有 | 无 |
| 复习 | 待确认积压，或以后的间隔复习到期 | 待确认事项、最近观察 | 以测评为主 | 测评 | 无 |
| 作业分析 | 在本地看作业 | 状态、代码 | 分析产出 | 自然表现 | 无 |
| 规划 | 学习者要求，或开场时模型认为有必要 | 全部状态、进度、目标 | 讨论接下来学什么 | 自述 | 计划（是否保存见议题 4） |

**结论。**

| 编号 | 结论 |
|---|---|
| 0.2-1 | 区分状态与证据：证据是发生过的事实，不可修改；状态由证据沉淀而成，可以修正；推断属于状态，并标明来源 |
| 0.2-2 | 证据分为自述、测评、自然表现三类；复述按由谁发起来归类；"保持"需要间隔才能观察到 |
| 0.2-3 | 核心循环：加载 → 互动 → 记录 → 沉淀；会话内依靠上下文即时调整，不需要每轮重新注入状态 |
| 0.2-4 | 各种场景是同一循环中不同的互动活动 |
| 0.2-5 | 证据由模型判断，值得记录就当即记录，必要时每轮都可以记。每个会话的证据记在一个文件中（原称 log），只追加；不变量改为"已记录的证据不再修改"。记录的单位是一条条证据：事实、证据类型、涉及的概念、情境（包括疲惫、赶时间这类临时状态，它们影响证据的诊断性）、时间，以及可选的、标为推断的当场理解。是否值得记录，由目标引导：它会不会改变或印证对学习者状态的认识，以后的模型是否需要知道它 |
| 0.2-6 | 沉淀自动进行，不需要学习者提出；下次加载时补做未完成的沉淀（幂等）；沉淀后给出简报。agent 客户端可以用会话结束的钩子提前沉淀 |
| 0.2-7 | 重大变更由服务端设为"待确认"，确认前不生效，每次加载时列出未处理的待确认事项；是否重大由模型判断；模型在回复中询问学习者，有结构化提问工具的客户端可以用它作为增强 |
| 0.2-8 | progress 自动更新且对学习者可见：开场一句话交代位置，简报中列出变化，随时可以查看和调整；较大的调整（跳过某一讲、修改截止日期）需要确认 |

### 0.3 学习者状态模型（已定）

**要解决的问题。**状态要覆盖哪些方面；各方面性质不同（变化快慢、粒度、由谁说了算），需要不同的更新和冲突规则；来源和把握程度要能表达，又不能让记录变得笨重；profile 能否由模型修改。

**状态的各个方面。**

| 方面 | 内容 | 粒度 | 变化快慢 | 主要来源 |
|---|---|---|---|---|
| 背景 | 学历、经历及实际参与的程度、大的领域上的基础 | 整体 | 很慢 | 自述为主，诊断和证据作补充 |
| 目标 | 长期方向、当前重点、每个资源的学习目的 | 整体或按资源 | 慢 | 自述 |
| 偏好 | 讲解方式、表达方式、节奏、检验强度 | 整体 | 慢 | 自述（含会话中的反馈），推断作补充 |
| 学习特征 | 学习方式上的特点：什么讲法有效或无效、反复出现的混淆、习惯、自评准不准 | 整体，跨主题 | 中 | 推断 |
| 知识掌握 | 每个概念理解到什么程度、在哪里容易出错、把握有多大、待确认之处；推断出的缺口也是其中的条目 | 按概念 | 快 | 测评、自然表现，自述和诊断作补充 |
| 进度与待续事项 | 在每个资源中的位置、截止日期；延后的问题、想了解的方向等以后要回到的事项（1.9 修订） | 按资源或按事项 | 快 | 外部事实加模型记录；待续事项来自学习者 |
| 待确认事项 | 尚未得到确认的状态变更和设定建议（议题 2 补充中区分为两类） | 按事项 | 快 | 系统 |

**由谁说了算。**

| 方面 | 谁说了算 | 理由 |
|---|---|---|
| 目标、偏好 | 学习者 | 想学什么、希望怎样被教，只有学习者能决定。模型可以指出不一致并提出，但不能自行改写 |
| 背景 | 学习者自述为主，证据可以补充或修正 | 经历只有学习者知道；"会不会某样东西"可以由证据更新 |
| 学习特征、知识掌握 | 证据 | 实际表现比自我感觉可靠，学习者可以对结论提出异议 |
| 进度 | 外部事实加模型记录 | 位置和截止日期是事实 |
| 待续事项 | 学习者 | 模型在学习者延后问题或表达想了解的方向时记下；是否放弃由学习者决定 |

原规则"自述与观察不一致时以观察为准"只适用于知识掌握，现由上表代替。

**来源和把握程度的最低要求。**状态中的每一条陈述，都要让以后的模型能回答四个问题：依据是什么类型（自述、测评、自然表现、推断）；什么时候；把握有多大（文字自由表达，但必须写出）；原始证据在哪里。除此之外写法不做规定。一条陈述可以同时包含多种来源，由模型综合写出判断。示意：

> 循环队列：能正确实现入队和出队，独立完成（测评，10-12）；判满的条件讲不清楚，两次把它和判空搞混（自然表现，10-12、10-15），把握较大。自述"学过"（自述，09-30），与表现不完全一致。

**不放进状态的内容。**临时状态（反复出现时才作为学习特征记录；但它会作为证据的情境被记录下来，见 0.2-5）；与学习无关的个人信息；原始证据本身（留在 log 中，状态只引用）。

**目标与偏好在实现中属于学习者设定（议题 2 补充）。**在业务模型中，目标和偏好仍是描述学习者的方面，由学习者说了算；在实现中，它们作为指令存放在学习者设定中，与描述性的状态分开（5.2-C：学习者设定存放在 profile/settings/；推断出的喜好作为学习特征，存放在 profile/descriptions/）。

**状态由主张组成（1.4 讨论中补充）。**以上各个方面，都可以看成范围和权威各不相同的主张。0.3-4 的四项最低要求，就是一条主张必须具备的属性。

**修改规则（议题 2 中修订）。**原表述为"模型可以补充，不能悄悄改写学习者的话"，学习者澄清其原意是"模型可以改写，但不能在学习者不知情的情况下改写"。在实现中，关于学习者本人的内容按性质分为学习者设定（指令）和学习者状态（描述），修改规则分别规定，见议题 2。5.2-C 进一步规定：设定只在学习者说出或确认后修改，沉淀和回顾不能修改；关于学习者本人的描述由沉淀和回顾维护，重大变更待确认，学习者知情。

**结论。**

| 编号 | 结论 |
|---|---|
| 0.3-1 | 状态包括背景、目标、偏好、学习特征（学习方式上的特点，含自评准确度）、知识掌握、进度与待续事项、待确认事项（1.9 修订：取消"疑问"；议题 2 补充：待确认事项分为待确认的状态变更和设定建议；实现中各方面的归属与存放见 2-5、5.2-24） |
| 0.3-2 | 推断出的缺口和待确认之处都并入知识掌握，不另设一类 |
| 0.3-3 | 各方面由不同的一方说了算，见上表 |
| 0.3-4 | 每条陈述必须能回答依据类型、时间、把握程度、证据位置四个问题，写法自由 |
| 0.3-5 | 临时状态、与学习无关的个人信息、原始证据不放进状态；临时状态作为证据的情境记录 |
| 0.3-6 | 模型可以改写关于学习者的内容，但不能在学习者不知情的情况下改写；会改变模型行为的修改须由学习者提出或确认（议题 2 修订） |
| 0.3-7 | 状态由主张组成，每条主张有范围和权威（1.4 讨论中补充） |

### 0.5 业务模型的整体结构（已定，1.4 讨论中补充）

**来由。**讨论推断流程时发现，我们的业务模型缺少明确的整体结构：没有区分"证据怎样更新认识"和"证据怎样被引出"，也没有说明教学与评估的关系。借用两类成熟的研究：以证据为中心的评估设计（ECD，Mislevy 等），它把评估拆为学生模型、证据模型、任务模型，并以"四过程架构"描述评估的运行；以及智能辅导系统（ITS）的经典结构：领域模型、学生模型、教学模型。对于开放式的对话辅导，学界没有统一的建模方法，这里只借用其结构，推理保持定性，不使用数值参数。

**组成部分与对应关系。**

| 组成部分 | ECD | ITS | 由什么承担 |
|---|---|---|---|
| 领域知识 | 无 | 领域模型 | 大模型的世界知识加学习材料（有意不保存，对应设计原则第 4 条） |
| 学习者状态模型 | 学生模型 | 学生模型 | 状态，即主张的集合（0.3） |
| 证据模型 | 证据模型 | 无 | 推断（1.4） |
| 引出模型 | 任务模型 | 无 | 互动中证据的引出（议题 4） |
| 教学 | 无 | 教学模型 | 讲解与检验（议题 4、6） |
| 学习过程模型 | 四过程架构 | 辅导循环 | 加载、互动、记录、沉淀（0.2） |

**学习过程模型与 ECD 四过程架构的对应。**

| ECD 的四个过程 | 学习过程模型 |
|---|---|
| 活动选择：决定下一个任务 | 互动中决定接下来做什么 |
| 呈现：给出任务、收集作答 | 互动 |
| 证据识别：从作答中提取证据 | 记录 |
| 证据积累：更新学生模型 | 沉淀 |

ECD 只关心评估：任务的目的只是获得证据。我们的大部分互动首先是在教学，证据是附带产生的，所以多出了教学这一部分。

**互动的两种价值。**每个互动行为同时具有学习价值（帮助学习者学会）和信息价值（让系统了解学习者）。最好的互动两者兼具，例如让学习者预测代码的输出：它是一次测评，而回忆和运用本身又能加深理解（测试效应）。这一点是议题 4"证据的引出"的核心输入。

**结论。**

| 编号 | 结论 |
|---|---|
| 0.5-1 | 业务模型由领域知识、学习者状态模型、证据模型、引出模型、教学、学习过程模型组成，结构借用 ECD 和 ITS |
| 0.5-2 | 领域知识由大模型和学习材料承担，不保存 |
| 0.5-3 | 互动同时具有学习价值和信息价值，引出证据时优先选择两者兼具的方式 |

**议题 0 至此完成。**

**归纳的三个层次：**

| 层次 | 内容 |
|---|---|
| 常驻（每次会话） | 偏好、目标、背景、学习特征、各资源的进度位置、待续事项、待确认事项、知识地图（按 D5，目前整份送入知识掌握） |

| 证据层 | 证据，由服务端按概念建立证据索引 |

上表沿用 0.3 的方面名称。实现中，目标和偏好中的要求属于学习者设定（profile/settings/）；推断出的喜好和讲法的效果属于学习特征（profile/descriptions/），见议题 2、5.2-C。

**带到后续议题的要点：**
- 知识掌握以外的方面单条很短，但几乎每个场景都要用到，属于常驻内容（议题 3）。
- 记录证据需要当前状态，知识地图在整个会话中都要可用（议题 3 的压缩恢复）。
- 自评准确度在诊断和判断前置中都要用到，冷启动时未知（1.4）。
- 学习者的意见：跨主题的个人化关联属于知识地图；可以设开关控制是否启用联想（暂缓区）。

### 1.2 知识掌握的条目（已定）

| 组成部分 | 作用 | 由谁负责 | 层次 |
|---|---|---|---|
| 名称、别名 | 标识；证据中用 `[[ ]]` 标注时使用同一名称 | 模型 | 约定 |
| 摘要 | 一句话说明当前掌握情况和置信程度；跨主题的个人化关联（如容易混淆的概念）；是否有待验证之处、是否存在已知误解（后两项 1.5 补充）。所有条目的名称加摘要构成知识地图 | 模型 | 约定 |
| 详情 | 理解到什么程度、在哪里出错、什么讲法对这个概念有效、待验证之处；每句话满足 0.3-4 的要求；提到其他概念时用 `[[ ]]` 标注；按"是否仍影响当前判断"决定保留哪些经过（1.5 补充） | 模型 | 目标 |
| 证据索引：相关证据、最近证据时间、涉及资源，以及各类证据的数量、首次证据时间（1.4 补充） | 追溯、检索，以及判断一个结论有多少依据 | 服务端根据证据中的概念标注计算 | 硬约束 |

**结论。**

| 编号 | 结论 |
|---|---|
| 1.2-1 | 条目由名称和别名、摘要、详情三部分组成，由模型维护；摘要是约定，详情只写明目标 |
| 1.2-2 | 证据索引由服务端计算，模型不再手工维护；前提是证据的概念标注可靠，这条约定因此更为重要 |
| 1.2-3 | 推断出的缺口使用同一种结构，摘要中写明"很可能未掌握"及其来源 |
| 1.2-4 | 暂不设置机器可读的状态等级；需要时（间隔复习、规划筛选、知识地图压缩）从摘要中提取，作为一次数据迁移 |

示例（仅作示意）：

> **循环队列**（别名：环形队列）
> 摘要：会实现入队、出队；判满条件不牢，容易与 [[判空条件]] 混淆；有待验证之处；置信程度较高。
> 详情：能正确实现入队和出队，独立完成（测评，10-12）。判满条件讲不清楚，两次与 [[判空条件]] 混淆（自然表现，10-12、10-15）。用"空出一个位置"的示意图讲解后当场能复述（测评，10-15），尚未在新题中应用，待验证。自述"学过"（自述，09-30），与表现不完全一致。
> 证据索引（服务端计算）：最近证据 10-15；涉及资源 ds-course；相关证据 3 条。

### 1.3 粒度与命名（已定）

**要解决的问题。**粒度太粗，摘要含糊、证据混杂；太细，条目膨胀、置信程度普遍偏低、标注更易出错；不同模型的粒度不一致会产生重叠的条目。命名分散（中英文混用、多种叫法、模型习惯不同）会让服务端计算的证据索引出错。条目必然需要改名、合并、拆分，而证据不可修改。

**粒度。**
- 标准：一个条目对应可以单独讲清、单独检验、且学习者的掌握程度可能与相邻内容不同的单位。两部分内容的教学决策不同时，应当分为两个条目。该标准以目标的形式交给模型判断，不规定大小。
- 先粗后细：新概念先按较粗的粒度建立；证据显示其中某部分的掌握明显不同且反复出现时，再拆分。
- 平铺，不保存层级；上下位关系由模型用世界知识理解。粗细两个条目只在都确有用处时并存。
- 可以学会、可以检验的技能和操作也作为条目，使用同一种结构；整体性的习惯属于学习特征，不建条目。

**命名。**
- 每个条目有一个正式名称（采用学习材料中最常用的叫法，由模型判断）和若干别名（其他叫法，含另一种语言）。取消"中文 (English)"的复合写法。
- 服务端计算证据索引时解析别名，比较时不区分大小写、忽略多余空格（硬约束）。
- 既不是正式名称也不是别名的标注称为未知标注。1.10 修订：写入证据时即由服务端拦下，并给出字面上相近的已有名称；模型确认是新概念时须明确声明，否则改用已有名称。声明的新概念由服务端即时登记为条目（5.2）。
- 证据不可修改，命名的修正只通过登记别名进行。

**演化。**

| 操作 | 做法 | 对证据索引的影响 |
|---|---|---|
| 改名 | 旧名称自动成为别名 | 无 |
| 合并 | 保留一个条目，另一个的名称和别名并入，详情由模型合并 | 证据自动合并 |
| 拆分 | 建立新条目，调整原条目详情；新条目详情中写明继承的旧证据（日期） | 新条目的索引只含之后的证据，旧证据通过详情中的引用追溯 |

改名、合并、拆分只改变状态的组织方式，不改变对学习者的判断，由模型在沉淀时执行，在会话简报中告知，不需要确认。需要专门的工具保证别名映射一致（议题 7）。

**结论。**

| 编号 | 结论 |
|---|---|
| 1.3-1 | 粒度以"教学决策是否不同"为标准，先粗后细、按证据拆分，平铺不存层级 |
| 1.3-2 | 技能和操作也作为知识掌握条目 |
| 1.3-3 | 正式名称加别名，取消复合名称；服务端解析别名；命名修正只通过别名进行。未知标注改为在写入证据时拦下，新概念须明确声明（1.10 修订） |
| 1.3-4 | 改名、合并、拆分由模型在沉淀时执行，在简报中告知，不需要确认 |

### 1.4 推断流程（已定）

**要解决的问题。**推断是模型从证据得出判断的过程，可能在七个地方出错：
1. 以偏概全：刚听完讲解就答对一道题，被记成已掌握。
2. 锚定：摘要每次会话都整份送入（D5），过时或错误的摘要会被后来的模型当成事实，不再检验，错误因此自我维持。
3. 模型之间的差异：不同模型的判断标准不同，同一个概念的结论被来回改写。
4. 自述的分量：自评可能偏高或偏低，冷启动时不知道自评准不准。
5. 遗忘：过去确认的掌握，今天未必成立。
6. 矛盾：前后的表现不一致。
7. 检验的分寸：推断过于乐观，难点会考两下就结束；过于保守，简单内容会被反复确认。

**范围。**推断发生在三个时刻：

| 时刻 | 模型在做什么 | 结果去哪里 |
|---|---|---|
| 会话中 | 根据刚出现的证据判断学习者当下懂没懂，决定下一步怎么讲、要不要检验 | 留在上下文；值得保留的当场理解，标明为推断，随证据记录 |
| 沉淀时 | 综合新证据和已有状态，更新状态 | 状态 |
| 使用时 | 加载后读取状态，用于教学决策 | 不产生记录 |

#### 统一的框架

逐条列出的经验原则难以保证系统和全面，因此建立一个统一的框架，所有方面的推断都由它推导出来。

**七个核心概念。**

| 概念 | 含义 |
|---|---|
| 主张 | 状态中的每一条陈述都是一个关于学习者的主张，例如"能独立实现循环队列""自评倾向于偏高" |
| 范围 | 主张覆盖的范围：一个概念、一个领域，或全局 |
| 权威 | 谁有权确立这条主张（0.3）：学习者，还是证据 |
| 诊断性 | 一条证据区分"主张成立"与"主张不成立"的能力：主张成立时很可能出现、不成立时不太会出现的证据，诊断性高 |
| 置信程度 | 综合所有证据后对主张的把握 |
| 时效 | 证据离现在越久，对"当前是否成立"的诊断性越低 |
| 信息价值 | 再获取一条证据是否值得：取决于当前的不确定性、即将做的决策是否依赖它、判断错误的代价，以及对学习者的打扰 |

**影响诊断性的因素（启发，不限于此）。**

| 因素 | 为什么影响诊断性 | 来源 |
|---|---|---|
| 独立完成还是提示后完成 | 有提示时，没懂也可能做对 | 经验 |
| 刚讲完还是隔了一段时间 | 刚讲完时短期记忆就足以答对 | 经验；对应 0.2 中的"保持" |
| 是否迁移到新情境 | 不真正理解，很难在新情境中用对 | 经验 |
| 自发运用还是被问到 | 自发运用说明知识能被主动调用 | 经验 |
| 证据类型 | 自述的诊断性取决于自评准确度 | 0.2、0.3 |
| 多次观察是否相互独立 | 相互独立的多次观察会叠加；同一次会话中的重复，叠加的效果有限 | 经验 |
| 题目的难度和区分度 | 答对很简单的题几乎说明不了什么 | 测量理论 |
| 猜对的可能 | 选择题、是非题容易猜对 | 知识追踪中的"猜对" |
| 当时的情境 | 疲惫、赶时间时出的错，对"没掌握"的诊断性较低 | 知识追踪中的"失误" |

**推断的五个操作（启发，作为思考路径，不是必须依次执行的步骤）。**

| 操作 | 做什么 | 要考虑的方面 | 由此得出的原则 |
|---|---|---|---|
| ① 形成主张 | 从证据的规律、背景和世界知识出发提出主张，例如推测某个前置知识存在缺口 | 有没有其他解释：一个错误可能是失误、记号不熟，也可能是概念没懂 | 缺口是假设；形成主张时先考虑其他解释 |
| ② 评估证据 | 判断新证据对相关主张的支持或反驳有多强 | 诊断性的各个因素 | 证据强弱取决于诊断性 |
| ③ 更新置信 | 按证据的诊断性修正置信程度 | 已有证据的积累、新证据的诊断性 | 置信程度与证据相称；没有新证据不改结论；一条弱证据不推翻多条强证据 |
| ④ 决定是否获取更多证据 | 权衡信息价值 | 不确定性、决策是否依赖它、判断错误的代价、对学习者的打扰 | 检验强度跟着不确定性走；防止锚定；冷启动时多观察、之后自然减少 |
| ⑤ 修订或退役 | 遇到反例，或长期没有再观察到时，修正或撤下主张 | 反例的诊断性、时效 | 主张可以被推翻；矛盾要保留；遗忘在使用时考虑 |

**矛盾的处理。**把矛盾看作几种相互竞争的解释（理解不稳定、一时失误、遗忘），在操作 ④ 中判断是否值得用一条能区分这些解释的证据去弄清楚。仍影响当前判断的矛盾证据在详情中保留，时好时坏本身就是信息；已被后续强证据取代的，压缩为一句说明（1.5 修订）。

**遗忘。**证据的诊断性随时间下降，在使用状态时考虑间隔，不定期批量改写状态：批量改写会产生没有新证据支撑的修改，违反可追溯；而遗忘的速度因人、因内容而异，固定规则并不准确。

**增量更新与重新评估（1.10 讨论中补充）。**从证据得出状态有两种方式：

| | 增量更新 | 重新评估 |
|---|---|---|
| 做法 | 在现有状态的基础上加上新证据的分量 | 不依赖现有结论，从相关的全部证据重新推导，替换原结论 |
| 读取的证据 | 尚未计入的新证据 | 全部相关的未撤销证据，可跨会话、跨很长时间 |
| 重复计入的风险 | 有，同一条证据计入两次会使置信程度虚高 | 无，每条证据在一次推导中只出现一次 |

操作 ③ 是增量更新；操作 ⑤ 以及必要时的整体推导属于重新评估。D7（推断可以重放）是对整个状态的重新评估。增量更新时可以查阅历史证据来理解新证据，但历史已体现在状态中，不再计入分量。

**提问的解读（1.9 补充，启发，不限于此）。**提问是诊断性最高的自然表现之一。上面的因素讨论一条证据有多大分量，这里讨论一个问题说明了什么：
- 问题的前提里假设了什么：错误的假设往往比错误的答案更能说明问题。
- 问的是哪个层次：是什么、为什么、何时不成立、与别的做法相比如何；层次越深，理解通常越深。
- 问题暴露了哪一环不确定：不知道某个事实，还是不理解两个概念之间的联系。
- 在什么时候问的：刚讲完就问，还是做题卡住才问。

**冷启动。**最初证据少、不确定性高，信息价值高，所以自然多观察；随着证据积累，检验也自然减少。这是操作 ④ 的结果，而不是规定的阶段。具体做法在议题 4 讨论。

#### 各方面的推断

学习特征是范围最大的主张，它的推断原则是框架的推论：

| 学习特征的原则 | 在框架中的位置 |
|---|---|
| 跨概念、跨时间的重复才构成学习特征；只在一个概念上出现的模式，留在那个概念的条目中 | 推广的范围要与证据的范围相称 |
| 描述行为，不给人定性，例如写"快速阅读时容易看漏 `~`、`&` 这类符号（三个不同概念）"，而不是"粗心" | 主张写成可观察的行为 |
| 写明适用范围和已知的反例 | 范围 |
| 学习特征可以被推翻；长期未再观察到或出现反例时调整，并保留变化过程 | 操作 ⑤ |
| 学习特征只为调整教学服务；学习者可以查看和提出异议；新增或明显改变的特征在简报中告知 | 目标：状态服务于教学决策 |
| 与学习者设定冲突时以设定为准，只能提出设定建议；与自述矛盾时属于重大变更，需要确认 | 权威 |
| 只描述学习上的行为，不推断健康、情绪或性格；临时状态只作为证据的情境（5.2-C） | 主张写成可观察的行为；0.3-5 |

学习特征的示意类型（启发）：有效或无效的讲解方式（效果）；表现出的喜好（例如倾向于直观的例子），喜好与效果可能不一致，作为两条主张分别记录（议题 2 补充）；跨概念的错误模式；元认知，例如自评偏高、过早说"懂了"（自评准确度属于此类）；学习过程中的习惯，例如卡住时很少主动提问。

**各方面主张的范围与权威。**

| 方面 | 范围 | 权威 | 推断能做什么 |
|---|---|---|---|
| 知识掌握 | 一个概念或技能 | 证据 | 形成、更新、修订主张 |
| 学习特征 | 跨概念或全局 | 证据 | 同上，推广的要求更高 |
| 背景 | 过去的经历 | 自述为主 | 作为推断与自述并列补充，不覆盖原话 |
| 偏好 | 全局 | 学习者 | 推断出的喜好作为学习特征记录在关于学习者本人的描述中（profile/descriptions/），可在设定允许的范围内直接参考；要成为设定中的指令，须作为设定建议经学习者确认（议题 2 补充） |
| 目标 | 全局或按资源 | 学习者 | 只能指出不一致 |
| 进度 | 一个资源 | 外部事实 | 判断某一部分是否学完，拿不准时在简报中写明 |
| 待续事项 | 一个事项 | 学习者 | 在学习者延后问题或表达想了解的方向时记下；回到它的时机由模型判断，放弃由学习者决定（1.9 修订） |

推断的操作对所有方面都相同，不同的只是范围和权威。

#### 按约束力整理（写入技能时的依据）

| 层次 | 内容 |
|---|---|
| 硬约束 | 每条主张可追溯到证据和日期，并标明依据类型；证据不可修改，状态由证据派生；由学习者说了算的主张及推翻自述的变更，经待确认机制才能生效 |
| 约定 | 没有新证据不改结论，认为以前的判断有错时写明理由；主张写成可观察的行为并附依据，不用"已掌握""粗心"之类的标签；主张写明范围，范围大的主张写明适用范围和反例；仍影响当前判断的矛盾证据在详情中保留，已被后续强证据取代的压缩为一句说明（1.5 修订）；学习特征只描述学习上的行为，不推断健康、情绪或性格（5.2-C） |
| 目标 | 状态服务于教学决策；置信程度与实际相称；推广的范围与证据的范围相称；主张可以被推翻；获取证据要值得（简单内容不反复确认，难点要有足够的证据） |
| 启发 | 主张、证据、置信的思考框架；推断的五个操作；影响诊断性的因素；学习特征的示意类型；各方面的范围与权威对照 |

**系统提供的支持。**证据索引增加各类证据的数量和首次证据时间，由服务端计算，让模型看到一个结论背后有多少依据、依据是否陈旧（并入 1.2）。

**结论。**

| 编号 | 结论 |
|---|---|
| 1.4-1 | 推断发生在会话中、沉淀时、使用时三个时刻 |
| 1.4-2 | 以主张、范围、权威、诊断性、置信程度、时效、信息价值七个概念为核心建立统一的推断框架；推断由五个操作组成，作为启发提供给模型 |
| 1.4-3 | 各方面的推断使用同一框架，差别只在范围和权威；学习特征的原则是框架的推论 |
| 1.4-4 | 推断的指导按约束力分属四层，见上表 |
| 1.4-5 | 证据索引增加各类证据的数量和首次证据时间 |
| 1.4-6 | 遗忘在使用时考虑；冷启动多观察是信息价值的自然结果 |
| 1.4-7 | 推断可以重放（D7），以试跑检验推断（D8） |
| 1.4-8 | 区分增量更新与重新评估；增量更新中历史证据只用于理解，不重复计入（1.10 讨论中补充） |

### 1.5 规模（已定）

**要解决的问题。**D5 规定知识掌握每次整份送入，以保证针对性讲解能看到完整的知识地图和掌握情况。需要判断这一做法在数据增长后何时出问题、怎样应对而不损害它的初衷。

**规模估算。**

| 项目 | 估计 |
|---|---|
| 条目数量 | 一门课约 40 到 80 个；本学期约 150 到 200 个；两年约 400 到 800 个 |
| 单个条目 | 摘要约 40 到 80 token；详情约 200 到 500 token |
| 整份送入 | 200 个条目约 6 万到 10 万 token；600 个约 15 万到 30 万 token |
| 只送摘要 | 200 个条目约 1 万 token；600 个约 3 万到 5 万 token |

**两个增长方向。**条目数量增加；单个条目的详情变长（如果详情不断追加观察）。

**规模变大后整份送入的代价。**占用上下文预算；注意力被稀释；压缩更频繁（议题 3）；被当作事实的旧摘要更多，锚定的面更大。整份送入的价值是覆盖完整，不会因未读到某个条目而漏掉联系。

**完整性的两个维度。**覆盖完整（每个条目至少以名称和摘要出现）与细节完整（全部详情）。两者的体积相差一个数量级：只要摘要写得足够好，覆盖完整几乎可以一直保持，需要控制的是细节完整。因此跨主题的个人化关联必须写进摘要。

**详情与历史。**此前的决定已保留了相当一部分历史：详情中的每句话注明证据类型和日期（0.3-4、1.2）；矛盾证据保留（1.4）；学习特征保留变化过程（1.4）。当时的理由是可追溯和推断质量，没有考虑详情的增长。完全不保留历史的代价是：以后的模型看不出理解的变化过程，要额外读取证据；保留什么交给沉淀时的模型，可能丢掉以后才发现重要的内容；学习者查看时透明度降低。完全保留历史的代价是详情只增不减。分界点是按"是否仍影响当前判断"决定保留什么，而不是按时间：
- 保留：支撑当前主张的关键证据；仍影响当前判断的矛盾。
- 压缩为一句：已被后续强证据完全取代、不再影响判断的经过。
- 完整历史始终在证据中，可通过证据索引查到；推断可以重放（D7），压缩时即使丢失了什么，也能从证据中重新得出。

**焦点范围的问题（分析结论，留作将来参考）。**按"证据出自当前资源"计算的焦点范围，反映的是出处，不是相关性。概念之间的相关性依赖模型的世界知识，服务端无法计算；跨资源的前置知识恰恰会被按出处的规则排除。因此将来需要控制细节时，读取哪些详情只能由模型根据完整的知识地图判断，服务端的规则至多提供基础范围（如有待验证之处、有待确认事项的条目）；漏读的风险靠摘要的质量来降低。

**体积的监控。**体积是给开发和维护者看的运行指标，不进入任何模型可见的流程：服务端在每次加载时写入运行日志，并提供管理命令（如 `learning-mcp stats`）供查看。

**结论。**

| 编号 | 结论 |
|---|---|
| 1.5-1 | 现阶段维持 D5，整份送入（3-B 修订：见 3-9） |
| 1.5-2 | 摘要增加跨主题的个人化关联，以及待验证之处和已知误解的提示（修订 1.2） |
| 1.5-3 | 详情按"是否仍影响当前判断"保留经过，已被取代的压缩为一句，完整历史在证据中；相应修订 1.4 中关于矛盾的约定 |
| 1.5-4 | 体积监控只在后端进行，不进入模型可见的流程 |
| 1.5-5 | 规模增长后的送入策略暂不决定，记入暂缓区；送入方式只影响服务端组装开场内容，不改变数据结构，以后调整不需要迁移（5.2-C：方向定为常驻知识地图、详情按需读取，见 5.2-33） |

### 1.6 沉淀：触发、范围与写入（已定，原 1.6 与 1.7 合并）

**要解决的问题。**
1. 未沉淀的证据会不会被遗漏：会话可能直接结束，补做可能没有完成，证据可能分散在多个会话中。
2. 沉淀由什么触发：模型不知道学习者何时离开；会话通常不会被主动关闭，离开也可能只是休息。
3. 沉淀的范围：日常沉淀只处理本次涉及的内容，而学习特征、合并与拆分、长期未验证的条目、缺口复核都需要跨越多次会话。
4. 写入的粒度：整份重写在规模变大后容易出错，也难以审查。
5. 重复与并发：补做可能执行两次；学习者可能同时在多个会话中学习。
6. 回退：沉淀的结论不满意，或证据来自被放弃的对话分支（例如编辑消息重发）。
7. 状态过期：长期打开或并行的会话中，开场加载的状态已被其他会话改变；每轮重新加载会分散注意力。

**加载。**开场概况给出未沉淀证据的情况，未沉淀的证据本身也一并送入。只给出状态而不送入证据，补做未完成时模型就会基于过时的状态教学。补做完成后，这些证据体现在状态中，不再单独送入。

**沉淀进度按单条证据记录。**每个会话的证据在一个文件中逐条追加。按文件记录会出错：收尾沉淀了证据 1 到 8，之后又追加了证据 9、10，按文件记录要么漏掉 9、10，要么重复处理 1 到 8。每条证据有编号，沉淀记录处理了哪些编号。

**时机。**沉淀不需要等信息足够：按 1.4 的框架，沉淀是按证据的分量更新置信程度，证据少时更新幅度小，这本身就是正确的结果。影响沉淀质量的是沉淀时上下文的完整程度，当前会话的模型看到完整对话，补做的模型只能看到记录下来的证据。

| 时机 | 由谁触发 | 说明 |
|---|---|---|
| 学习者给出结束信号（"收尾""沉淀"等） | 学习者 | 效果最好的方式 |
| 一个段落结束（学完一个小节、切换主题、学习者表示休息） | 模型自动判断 | 判断很轻，与教学中原本的判断相同 |
| 下次加载时补做 | 系统提示，模型执行 | 兜底 |

不使用会话结束的钩子：会话通常不会被主动关闭，离开不代表到了沉淀的时机。

**会话标记。**服务端无法从请求本身知道它来自哪一次对话：MCP 传输层的会话标识对应的是连接，网页端怎样复用连接不受我们控制，只能在实测后作为辅助。因此由服务端在开场加载时发放会话标记，模型在之后的每次工具调用中原样带上；证据的归属、会话已知的修订、增量的计算、会话是否闲置，全部由服务端完成。每次工具结果都重复给出标记，降低压缩时丢失的风险；agent 客户端可用钩子在压缩后重新注入。标记丢失时模型重新加载，开启新会话，原会话的证据按跨会话的规则处理，不会丢失。具体结构见 1.10。

**跨会话的沉淀。**
- 每次沉淀只针对一个会话的证据。本会话沉淀时，计入的只有本会话的新证据，依据现有状态和本会话的对话上下文；其他会话未沉淀的证据不用于沉淀（它们随加载送入，可供教学参考）。这样同一批证据不会被计入两次。已计入的历史证据可以查阅，用来理解新证据，但不再计入分量。
- 闲置的会话：服务端根据会话标记的最后写入时间判断，闲置时间超过阈值（配置项）的会话，其证据由新会话代为沉淀，只依据那个会话的证据（原会话的上下文已不可得），作为单独的一次沉淀提交，在简报中说明。
- 学习者随时可以要求代为沉淀某个会话的证据，或回到原会话沉淀。
- 回顾是跨会话的，见下文。

**两种沉淀。**

| | 日常沉淀 | 回顾 |
|---|---|---|
| 何时 | 上述三种时机 | 到期后，在学习结束之后进行 |
| 处理什么 | 本会话证据涉及的条目，以及涉及的其他方面（关于学习者本人的描述即背景和学习特征、待续事项、进度；不包括学习者设定，5.2-C）；对单个条目可以选择增量更新或重新评估 | 跨会话的重新评估：读取长时间跨度内的全部未撤销证据（不论是否已沉淀），关注学习特征的规律、合并与拆分、长期没有新证据的条目、缺口的复核、长期未处理的待续事项 |
| 由谁执行 | 当前会话的模型 | agent 客户端交给子代理，不占主对话上下文；网页端在主对话中进行 |

**回顾的触发：两者结合，满足任一即到期。**
- 服务端按可计算的事实性指标判断：距上次回顾的会话数和证据数、长期没有新证据的条目数、上次回顾以来新登记的条目数（5.2 修订：原为"未处理的未知标注数"，1.10 之后不再存在）、长期未处理的待续事项数。阈值为配置项。
- 模型注意到值得回顾的情况时（例如发现可能影响许多条目的误解、学习目标发生变化），可以主动提出并写明理由。这属于启发层，没有特别发现时不需要考虑，不增加日常的注意力负担。
- 服务端没有语义理解能力：它能提供的候选只限于事实性的指标（如长期没有新证据的条目、上次回顾以来新登记的条目）；证据是否相互矛盾、跨概念的规律、该合并或拆分的条目，由模型在回顾中发现。
- 回顾时可以留意新登记的条目是否与已有条目重复、粒度是否一致；这属于启发，不作约束（5.2）。
- 回顾在学习结束后进行，以免占用教学的上下文；信号在完成前一直保留。

**写入。**只重写涉及的条目，其余条目不动。一次沉淀产生的全部修改（知识掌握条目、关于学习者本人的描述、待续事项、进度、新的待确认事项；不包括学习者设定，5.2-C），连同"这些证据已沉淀"的标记，作为一个整体提交，要么全部生效，要么全部不生效。已标记的证据不会再被增量更新计入，因此沉淀是幂等的。"已沉淀"的标记只约束增量更新，重新评估可以读取任何未被撤销的证据（1.10 讨论中补充）。回顾所需的证据由服务端按概念、时间范围、证据类型筛选并分页提供。沉淀必须基于最新的修订，基于过时版本的提交会被拒绝，模型读取最新状态后重做。

**回退与撤销：两个独立的操作。**

| 操作 | 做什么 | 何时使用 |
|---|---|---|
| 回退沉淀 | 状态恢复到这次沉淀之前，相关证据变回未沉淀 | 对沉淀的结论不满意 |
| 撤销证据 | 追加一条撤销记录，这些证据不再参与沉淀和证据索引；原记录保留 | 证据本身不应计入，例如来自被放弃的对话分支，或基于错误的材料 |

两者可以组合：先回退，再撤销不应计入的证据，然后重新沉淀（D7）。服务端无法知道学习者在网页上编辑了消息，所以由学习者发起；简报中列出本次记录和沉淀的内容，帮助学习者及时发现问题。回退的前提、与之后的改动冲突时的做法见 5.2-A。

**状态过期。**状态带修订号，每次改变设定或状态的提交后加一（5.2 修订：原称"版本号"，只随沉淀增加）。服务端通过会话标记知道每个会话已知的修订；会话调用任何工具时，如果它已知的修订已过时，工具结果中附带简短的增量说明（哪些条目发生了变化），模型只读取与当前内容相关的变化，不重新加载全部。这一机制也用于议题 3 的压缩恢复和去重。（3-C 修订：学习者设定的变化立即附上全文；其他变化只在状态行中标记数量，由模型按需获取，见 3-19。）

**简报的依据。**每次沉淀是一个整体提交，服务端可以算出提交前后状态的结构性差异，交给模型作为写简报的依据。简报的内容在议题 4 讨论。

**按约束力整理。**

| 层次 | 内容 |
|---|---|
| 硬约束 | 加载时送入未沉淀的证据；沉淀进度按单条证据记录；会话标记由服务端发放和追踪；一次沉淀整体提交、幂等、基于最新版本；回退与撤销由服务端执行且保留记录；重大变更进入待确认状态 |
| 约定 | 每次沉淀只针对一个会话的证据；本会话沉淀只用本会话的证据和上下文；日常沉淀覆盖证据涉及的所有方面；按条目写入；每次工具调用带上会话标记 |
| 目标 | 状态始终是最新的、准确的；回顾让跨会话的规律有机会被发现 |
| 启发 | 什么时候算一个段落结束；什么情况值得主动提出回顾；回顾时值得关注的方面 |

**结论。**

|---|---|

| 1.6-2 | 沉淀进度按单条证据记录 |
| 1.6-3 | 沉淀的时机：学习者的结束信号、段落结束时模型自动进行、下次加载时补做；不用会话结束的钩子 |

| 1.6-10 | 简报以服务端计算的提交前后差异为依据 |

### 1.9 学习者的疑问（已定：取消"疑问"作为独立的状态方面）

**要解决的问题。**最初的需求要求记录"疑惑点"，0.3 据此设了"疑问"这一方面。但会话中的大多数问题只是例行的问答，记录价值不高；有些问题则能体现思维方式和知识漏洞。需要判断"疑问"是否真正具有独立的价值。

**一个问题的两种价值。**诊断价值：这个问题透露了学习者的什么。待续价值：这个问题还没有了结，以后要回到它。

| 问题的类型 | 例子 | 诊断价值 | 待续价值 | 去处 |
|---|---|---|---|---|
| 例行的问答 | 问一个事实，听完就懂 | 低 | 无 | 不需要记录 |
| 前提里带着误解 | "中断里不能延时，是因为会关掉别的中断吗？" | 高 | 无 | 证据 → 知识掌握（误解） |
| 提问的层次或角度 | 问设计动机、边界条件、替代做法 | 高 | 无 | 证据 → 知识掌握；反复出现时 → 学习特征 |
| 反复问同一类问题 | 多次问相似术语的区别 | 高 | 无 | 证据 → 学习特征 |
| 解答后仍然没懂 | "我还是不明白为什么要留一个空位" | 高 | 有 | 证据 → 知识掌握（误解或待验证之处） |
| 延后的问题、超出范围的好奇 | "这个以后再说""我想以后了解一下 X" | 低 | 有 | 待续事项 |

**结论。**"疑问"原本承担的价值都有了更合适的去处：诊断价值通过证据流入知识掌握和学习特征（提问本就属于自然表现，且是诊断性最高的一种）；"解答后仍然没懂"属于知识掌握中的误解或待验证之处，摘要会提示它们（1.5），在相关时会被重新提起；只剩下延后和好奇的问题，它们是以后要回到的事，性质与进度相同。最初需求中的"记录疑惑点"依然满足，分为两处：真正的困惑在知识掌握中，延后的问题在待续事项中。

| 编号 | 结论 |
|---|---|
| 1.9-1 | 取消"疑问"作为独立的状态方面 |
| 1.9-2 | "进度"扩展为"进度与待续事项"；待续事项由学习者说了算：模型在学习者延后问题或表达想了解的方向时记下，是否放弃由学习者决定 |
| 1.9-3 | 1.4 的启发层增加"提问的解读" |
| 1.9-4 | 相应修订 0.3、1.1、1.4、1.6 中涉及"疑问"的内容 |

### 1.10 证据与会话的记录结构（已定）

**要解决的问题。**1.6 的机制（会话标记、按单条证据记录沉淀进度、整体提交、回退、撤销、修订、增量告知）都需要对应的记录才能运转。需要确定记录哪几类东西、各包含什么、怎样关联、有哪些不变量。文件格式留给 1.8 和议题 5。贯穿全局的难点是：证据不可修改，但它的"是否已沉淀""是否被撤销"会变化，所以凡是会变化的信息都放在其他记录中，通过编号指向证据。

**六类记录。**

| 记录 | 包含什么 | 谁来写 | 可变吗 |
|---|---|---|---|
| 会话 | 会话标记、创建时间、客户端名称、模型自报的名称、插件版本（5.2-B）、可选的平台会话标识（3-C） | 服务端 | 不可变（5.2 修订：最后写入时间由该会话最后一条证据推导；已知的修订作为运行数据保存在服务器本地，不进 git） |
| 证据 | 编号、所属会话、时间、类型、发生的事实（必要时引用原话）、涉及的概念（结构化字段）、情境（含临时状态、所用材料、给出的任务）、所属资源、可选的当场理解（标为推断） | 模型提供内容，服务端补充编号、会话、时间 | 不可变 |
| 更正 | 指向的证据、类型（撤销、补充情境、更正标注）、理由、时间、发起者 | 学习者发起，服务端执行；更正标注也可由模型在沉淀和回顾中发起（5.2） | 只追加 |
| 沉淀记录 | 编号、执行沉淀的会话、证据所属的会话、计入的证据（增量更新）、读取的证据范围（重新评估）、前后的修订、类型（日常、补做、代为、回顾、学习者要求）、针对的沉淀（学习者要求时，5.2）、服务端计算的结构差异 | 服务端在提交时生成 | 不可变 |
| 回退记录 | 回退的沉淀、回退后的修订、理由 | 学习者发起，服务端执行 | 不可变 |
| 修订（5.2 前称"状态版本"） | 修订号、产生它的操作（见 5.2-A）、改动了哪些条目和方面 | 服务端 | 不可变 |

会变化的信息都由不可变的记录推导：证据是否已计入（是否有未被回退的沉淀记录计入了它）、是否被撤销（是否有撤销记录）、会话是否闲置（该会话最后一条证据的时间）、两个修订之间的增量（期间各修订记录的改动之和）。这些都是确定的计算，不需要语义理解。

**设计说明。**
1. 证据编号全局递增，跨会话可直接比较先后，便于沉淀记录引用；编号永不复用。
2. 时间以服务端为准，模型对当前时间的判断不可靠。
3. 概念标注是证据中的结构化字段，证据索引依赖它；正文中可继续用 `[[ ]]` 方便阅读。
4. 未知标注在写入时拦下：匹配正式名称或别名的直接写入；不匹配的拒绝写入，并给出字面上相近的已有名称（按字符串相似程度计算，不涉及语义）；模型确认是新概念时须明确声明。判断"新概念还是已有概念的另一种叫法"由模型完成，服务端只负责发现"这个名字没见过"并给出候选。这修订了 1.3 中在沉淀时报告未知标注的做法。声明的新概念由服务端即时登记为条目（5.2）。
5. 会话记录客户端名称（服务端从 MCP 连接中得到）和模型自报的名称（标明为自报），每条证据、每次沉淀都能追溯到模型，服务于 D8 中对不同模型的比较。

**不变量（硬约束）。**
1. 证据、沉淀记录、回退记录、修订记录写入后不再修改；更正只追加。
2. 编号永不复用。
3. 一条证据最多被一次有效的增量更新计入；所在的沉淀被回退后，才能再次计入。重新评估可以读取任何未被撤销的证据。
4. 被撤销的证据不参与沉淀，也不进入证据索引。
5. 沉淀和回退都是整体提交，并基于最新的修订。
6. 时间由服务端生成。
7. 概念标注必须匹配已有的名称或别名，或被明确声明为新概念。

**结论。**

| 编号 | 结论 |
|---|---|
| 1.10-1 | 六类记录：会话、证据、更正、沉淀记录、回退记录、修订（5.2 前称"状态版本"）；会变化的信息不写在证据上，由其他记录推导；会话记录不可变（5.2 修订） |
| 1.10-2 | 证据编号全局递增、永不复用；时间以服务端为准 |
| 1.10-3 | 概念标注为结构化字段；未知标注在写入时拦下，新概念须明确声明；声明的新概念即时登记为条目（5.2） |
| 1.10-4 | 会话记录客户端名称和模型自报的名称；还保存插件版本（5.2-B）和可选的平台会话标识（3-C） |
| 1.10-5 | 不变量见上；回退较早沉淀时的冲突问题已在 5.2 解决 |

## 3B. 议题 2：关于学习者本人的状态（已定）

**要解决的问题。**背景、目标、偏好、学习特征怎样组织和存储；模型和学习者都会修改这些内容，如何避免冲突；权威和来源如何在存储上体现。

**曾考虑的方案及放弃的原因。**最初按写入者划分：学习者写的 profile 与模型维护的个人状态分开，每个文件只有一个写入者。但这样自述、目标、偏好在两边都会出现，而且它把"学习者对模型的指令"和"模型对学习者的描述"混在了一起。其根源是把 0.3 的修改规则理解成了"模型永远不能改动学习者写的文字"，比学习者的原意更严格。

**按性质区分：指令与描述。**

| | 指令 | 描述 |
|---|---|---|
| 例子 | "别用强行的类比""这学期重点学某门课的 lab" | "没有系统学过数据结构""先给例子再讲原理时复述更准确" |
| 模型怎样对待 | 遵守 | 作为判断的依据，按置信程度权衡 |
| 与协作说明的关系 | 可以覆盖 | 不覆盖，只提供信息 |
| 谁说了算 | 学习者 | 证据，或学习者的自述作为一种证据 |
| 怎样改变 | 学习者表达或确认后才改 | 随证据自动更新 |

混在一起会出两种错：把描述当作命令执行；把指令当作可以权衡的信息。

| 部分 | 性质 | 包含什么 |
|---|---|---|
| 学习者设定 | 指令 | 讲解和表达方式的要求、学习者的反馈、学习目标、每个资源的学习目的 |
| 学习者状态 | 描述，主张的集合，每条带来源 | 背景（自述与推断并存，靠来源标注区分）、学习特征、知识掌握、进度与待续事项 |

这与 0.3 的权威划分吻合：由学习者说了算的方面属于设定，由证据说了算或两者兼有的方面属于状态。每一项只存在于一处：会话中说"别用这种讲法"写入设定；说"上学期学过数据结构"作为自述主张写入状态；说"这学期重点学某门课"写入设定；模型推断出的喜好和讲法的效果是描述，作为学习特征记录在状态中，可直接参考；模型也可以提出设定建议，确认后才成为设定中的指令（见本节补充）。

**修改规则。**
- 设定：模型只在学习者明确表达要求，或确认了模型的设定建议时修改；每次修改都在简报中告知。
- 状态：模型按 1.6 自动维护；重大变更进入待确认状态，其余在简报中告知。
- 学习者可以直接修改设定和状态；对状态的直接修改记为来源为自述的变更，产生一次修订（1.10、5.2）。

**写入冲突。**不要求每个文件只有一个写入者。模型的写入都经过服务端，写入前先拉取；学习者在本地修改后通过 git 推送；改的是同一文件的不同部分时由 git 自动合并；改到同一处时，服务端放弃这次写入并报告，不覆盖学习者的修改。

**模型维护的个人状态的结构。**沿用知识掌握条目的结构（名称、摘要、详情，每句话说明依据类型、时间、置信程度和证据位置）。学习特征暂不在证据上单独标注，由模型在沉淀和回顾中从证据的规律归纳，在详情中写明依据的证据日期；需要更精确的索引时再增加（C3）。

**加载顺序。**协作说明 → 学习者设定 → 学习者状态（背景、学习特征、知识掌握、进度与待续事项）。设定紧跟协作说明，因为它覆盖协作说明。会话中的指令与设定文件中的内容不一致时，较新的优先，模型在简报中指出并建议更新；一时的要求属于临时状态，不记录为指令。

**对现有结构的影响。**profile/ 改为只存放学习者设定，约定不变（自由组织，全部读入，与协作说明不一致时以它为准）；现有 10-learner.md 中的背景移入状态，作为来源为"自述，2026-09"的主张（重构时一并迁移）；每个资源的学习目的属于设定，可以与进度存放在一起，但修改须经学习者。（5.2-C 修订：profile/ 改为关于学习者本人的内容，分 settings/（学习者设定）和 descriptions/（关于学习者本人的描述：背景、学习特征）；设定每条一个文件，学习者自由写的文件模型只读，不再是"自由组织"；学习目的存放在 settings/resources/，呈现时与进度放在一起；系统尚未运行，10-learner.md 不再迁移，背景以后再写。见 5.2-C。）

**结论。**

| 编号 | 结论 |
|---|---|
| 2-1 | 关于学习者本人的内容按性质分为学习者设定（指令）与学习者状态（描述） |
| 2-2 | 设定由学习者表达或确认后才修改，每次修改都告知；状态由模型自动维护，重大变更待确认（5.2-C 细化：沉淀和回顾提交的改动不能触及设定，见 5.2-25） |
| 2-3 | 写入冲突由服务端处理（写入前拉取，改到同一处时放弃并报告），不要求单一写入者 |
| 2-4 | 模型维护的个人状态沿用知识掌握条目的结构；学习特征暂不在证据上单独标注 |
| 2-5 | profile/ 只存放设定；背景移入状态；学习目的属于设定（5.2-C 修订：profile/ 改为关于学习者本人的内容，分 settings/ 与 descriptions/；背景和学习特征存放在 descriptions/；学习目的存放在 settings/resources/，见 5.2-24） |
| 2-6 | 加载顺序：协作说明、学习者设定、学习者状态 |

**补充（议题 5 讨论期间）：推断出的喜好与两类待确认事项。**

问题：模型自己推断出的偏好放在哪里。"先总览再细化时表现更好"是效果，已有位置（学习特征中有效或无效的讲解方式）；"似乎更喜欢直观的例子"是喜好，按此前的规定只能作为提议、确认后成为设定，这意味着确认之前它既无处存放，也不能被使用。

解决：分成两件互不依赖的事。
- 喜好是描述，作为学习特征记录在状态中，沉淀时按证据正常更新，不需要确认；模型在设定允许的范围内可以直接参考。喜好与效果作为两条主张分别记录：学习者喜欢的讲法不一定是学得最牢的讲法，两者冲突时怎样取舍属于教学问题（议题 4、6）。
- 模型可以提出设定建议，把某条喜好变成固定的指令。确认前设定和状态都不改变；确认后加入设定并在简报中告知；与已有指令冲突时，建议中写明会替换哪一条；被拒绝时设定不变，拒绝本身被记录，没有明显更强的新证据时不重复建议。学习特征中是否记下这条喜好，与建议是否被接受无关。

示例：几次会话中记下"给出例子后接连提问""长推导直接跳过"等证据 → 沉淀时写下学习特征"喜好：倾向于直观的例子（置信程度中等）" → 设定中没有相关要求时，模型多用例子 → 模型提出设定建议，接受则成为指令，拒绝则一切照旧 → 若设定中写着"多讲推导"，这条喜好不能推翻指令，只能提出写明替换关系的建议。

两类待确认事项：

| | 待确认的状态变更 | 设定建议 |
|---|---|---|
| 来自 | 0.2-7 | 0.3、议题 2 |
| 改变什么 | 状态（对学习者的描述） | 设定（对模型的指令） |
| 例子 | 判定某个概念存在缺口；推翻学习者的某条自述 | 把"先给直观的例子"加为固定要求 |
| 谁有权决定 | 本属证据说了算，确认是让学习者能够否决的安全措施 | 本就由学习者说了算，模型只能建议 |
| 共同点 | 确认前不生效；由服务端保存，每次加载时列出未处理的；拒绝也被记录 | |

| 编号 | 结论 |
|---|---|
| 2-7 | 推断出的喜好作为学习特征记录在关于学习者本人的描述中（5.2-C），可在设定允许的范围内直接参考；喜好与效果分别记录 |
| 2-8 | 设定建议确认前不改变任何东西；冲突时写明替换关系；拒绝被记录，避免重复建议 |
| 2-9 | 待确认事项分为"待确认的状态变更"和"设定建议"两个术语 |

## 3C. 议题 5：数据架构与演进（已定）

分两轮：5.1 每类数据用什么形态存储（即原 1.8）；5.2 版本、迁移与 git 的角色（又分 5.2-A、5.2-B、5.2-C 三轮）。

### 5.1 存储形态（已定，含原 1.8）

**要满足的要求。**

| 要求 | 来自 |
|---|---|
| 证据不可修改、只追加；能按概念、时间、类型筛选 | 1.6、1.10 |
| 一次沉淀改动的多个条目整体生效；基于最新版本；幂等 | 1.6 |
| 状态和设定可由学习者直接阅读和修改，git 差异可读 | 议题 2、可追溯 |
| 状态带修订号，能算出修订之间的增量 | 1.6、1.10 |
| 派生数据可以删除重建 | 演进与迁移 |
| 推断可以重放 | D7 |
| 数据组织方式会演进，要能迁移 | D2 |
| 知识掌握整份送入 | D5 |
| 服务端只理解结构，不理解语义 | 1.6 中的修正 |

**规模。**两年内状态条目约 400 到 800 个；证据约几千条，总量几 MB。存储性能不是问题，需要权衡的是可读性、可修改性和可靠性。

**四类数据的形态。**

| 数据 | 性质 | 形态 | 理由 |
|---|---|---|---|
| 记录：会话、证据、更正、沉淀记录、回退记录、修订、待确认的状态变更与设定建议 | 只追加，结构化 | JSON Lines | 只追加对应不可修改；git 差异只显示新增行；字段结构化，服务端可直接筛选；纯文本，人也能读 |
| 状态：知识掌握条目、学习特征、背景主张、进度与待续事项 | 会修改，学习者要读和改 | Markdown，开头用 YAML 写结构化字段（名称、别名、编号等），正文写摘要和详情 | 可直接阅读和编辑；服务端只读结构化字段，不解析正文 |
| 设定：profile/settings/ | 学习者；模型在学习者说出或确认后写 | Markdown：每条一个文件，写明做什么、为什么；另有各资源的学习目的和学习者自由写的文件 | 议题 2、5.2-C |
| 派生数据：证据索引、以后的摘要和检索索引 | 可删除重建 | 服务端启动时在内存中计算，或缓存到不进 git 的目录（如 SQLite 文件） | 不是原件，可从记录和状态重新算出 |

证据按会话分文件，对应 0.2-5"每个会话的证据记在一个文件中"；编号仍全局递增。其他记录按类型各一个文件，过大时按月分开。

**知识掌握每个条目一个文件。**

| | 一个大文件 | 每个条目一个文件 |
|---|---|---|
| 整份送入 | 直接读取 | 服务端拼接，同样简单 |
| 修改一个条目 | 差异大，易与学习者的修改冲突 | 只动一个文件 |
| 学习者查看或编辑 | 要在长文件中查找 | 直接打开 |
| 一次沉淀改动多个条目 | 天然在一起 | 放进同一次 git 提交，提交本身整体生效 |
| 改名 | 改一行 | 文件改名，git 识别为重命名 |
| 将来兼容 Obsidian | 困难 | 自然：`[[ ]]` 指向同名的条目文件，数据仓库可直接作为 Obsidian 库打开（5.2-C 修订：库为仓库根目录） |

**文件名与编号。**文件名用正式名称（服务端替换文件名中不允许的字符，并处理大小写冲突）；每个条目另有稳定编号，写在结构化字段中；所有记录通过编号引用条目。证据写入时，服务端已把概念标注解析到条目（1.10），因此证据同时保存写下的名称和解析得到的编号；条目改名不影响引用；条目合并时，服务端记录"旧编号并入新编号"，证据索引依然正确。这比只靠别名解析更可靠。

**整体提交的实现。**服务端先把一次沉淀的全部改动写到临时位置，全部成功后一次性移入并做一次 git 提交；任何一步失败就放弃全部改动。配合写入锁和版本检查（1.6），保证整体生效、基于最新版本、不重复处理。这是服务端的工程实现，不需要模型参与。

**结论。**

| 编号 | 结论 |
|---|---|
| 5.1-1 | 记录用 JSON Lines，只追加；状态用带结构化开头的 Markdown；设定的组织见 5.2-26；派生数据可重建，不进 git |
| 5.1-2 | 知识掌握每个条目一个文件，开场时由服务端拼接后整份送入 |
| 5.1-3 | 文件名用正式名称，条目另有稳定编号；记录通过编号引用条目；证据同时保存写下的名称和解析得到的编号；合并时记录编号的并入关系 |
| 5.1-4 | 证据按会话分文件，其他记录按类型分文件 |
| 5.1-5 | 整体提交由服务端实现：临时写入、一次移入、一次提交，失败则全部放弃 |

### 5.2 版本、迁移与 git 的角色（已定）

分三轮：5.2-A 历史（git 的角色、修订、回退）；5.2-B 版本与迁移；5.2-C 数据仓库的目录布局与初始化。回退怎样做、迁移失败怎样回滚，都取决于谁记录历史，所以先讨论 5.2-A。

#### 5.2-A 历史：git 的角色、修订与回退（已定）

**要解决的问题。**
1. 三方需要历史：会话需要知道加载之后发生的变化（1.6-9 的增量）；回退需要沉淀之前的内容（1.6-8）；学习者和备份需要异地保存、在本地查看和修改、出问题时能追溯。
2. 写入方不止一个：服务端（代模型写入）、学习者（本地修改后推送）、迁移。
3. git 天然保存每个文件的完整历史。问题是让 git 历史同时承担上述职责，还是让 1.10 的状态版本记录独立存在。
4. 回退较早的沉淀时，之后的沉淀可能改动过同一条目（原暂缓区"版本管理"）。

**git 历史不适合作为逻辑上的历史。**
1. 提交编号不稳定：服务端拉取时用 rebase，尚未推送的本地提交在学习者推送新提交后会被重新生成，编号随之改变。
2. git 只认文件，不认条目：改名是路径变化，合并是一个文件删除、另一个修改。要知道哪个条目变了，需要解析前后两版的结构化开头，而这些信息服务端写入时本来就知道。
3. 提交的粒度和含义不统一：证据追加、学习者一次推送中的多处修改、迁移对全部文件的改写都是提交，其中只有一部分是状态的变化。
4. 可迁移性（D2）：数据的组织方式会变，逻辑上的历史要能跟着数据走；推断重放（D7）和增量计算只需要记录。

**方案：修订记录是逻辑历史，git 是物理历史。**

| | 修订记录 | git |
|---|---|---|
| 回答的问题 | 哪一次操作、由谁发起、改了哪些条目和设定 | 某一时刻每个文件的完整内容 |
| 用于 | 增量、追溯、判断能否回退、重放 | 回退时取回旧内容；备份；与学习者本地同步 |
| 对应方式 | 每个修订对应一次提交，提交说明末尾写上修订号（如 `Cairn-Revision: 42`）。提交编号改变后这一行仍在，按修订号就能找到对应的提交 | |

修订记录由服务端在同一次提交中生成，不经过模型。

**术语：修订。**"状态版本"改称"修订"（revision）：设定或状态（含待确认事项）的每一次变化产生一个修订，修订号全局递增；增量是两个修订之间的变化；"版本"只用于软件和格式。原因有两个：议题 2 之后，需要告知会话的变化包括设定和状态两部分，1.10 中"学习者修改 profile 产生状态版本"已不准确；5.2-B 会出现插件、服务端、数据格式的版本，"版本"不能同时指内容的一次变化。

产生修订的操作：各类沉淀；回退；设定修改（学习者在会话中提出，或确认设定建议）；待确认事项被确认或否决；学习者在本地直接修改；资源的加入与更新（议题 9）；迁移；新概念登记（见下文）。

**学习者的本地修改。**服务端每次拉取后，比较拉取前后 state/ 和 profile/ 的变化，通过结构化开头中的编号对应到条目，生成一个"学习者修改"修订（对状态的修改来源为自述，议题 2）；同时做结构检查（编号缺失、名称或别名重复等），问题在下一次工具结果中报告。

记录文件只能追加：服务端拉取后检查已有的行是否被改动；如有，从 git 恢复原内容并报告，说明证据需要更正时用更正记录。这是不变量 1 在 git 通道上的落实。

**git 中放什么。**
- 进 git：记录、状态、设定。
- 不进 git：派生数据（5.1）；运行数据。会话"已知的修订"随每次附带增量的工具结果更新，变化频繁且不需要历史，保存在服务器本地；丢失时（例如重启），按会话加载时的修订重新告知一次增量。会话的最后写入时间由该会话最后一条证据的时间推导，不单独保存。
- 会话记录因此不再变化，与 1.10"会变化的信息由不可变的记录推导"一致（修订 1.10 的会话记录）。

**提交与推送。**每次写入在服务器本地提交一次，工作区始终干净，拉取和沉淀的整体提交都更简单。
- 证据追加：只在本地提交，推送在后台合并进行，写入证据不必等网络。学习者不修改证据文件（改了也会被恢复），后台推送不会与学习者的修改冲突。
- 改动状态或设定的写入（沉淀、回退、设定修改）：写入前拉取，写入后立即推送；推送时发现学习者改了同一处，放弃这次写入并报告，2-3 的冲突处理照常成立。
- 证据的提交会很多（两年几千个），对 git 不是负担；查看状态的历史时可只看 state/ 目录。拉取的时机属于实现，在议题 10 决定。

**备份。**服务器磁盘、GitHub 私有仓库、学习者本地的 clone 共三份，不另设备份。前提是数据仓库的历史不被改写（不强制推送），这一条写入数据仓库的说明。

**回退较早的沉淀。**

例：第 12 次沉淀把"中断优先级"写成"很可能未掌握"；第 15 次沉淀在此基础上补充"能区分抢占优先级和响应优先级，嵌套时仍混淆"；学习者发现第 12 次依据的证据来自放弃的对话分支，要回退第 12 次。恢复到第 12 次之前，第 15 次的补充会一起丢失；保留第 15 次的内容，它又是在第 12 次的结论上写的。

条目的内容不是可以单独揭下的补丁，第 15 次是读了第 12 次的结论后重写的综合判断。"去掉第 12 次的影响、保留第 15 次的贡献"需要理解内容，服务端做不到。因此服务端只在没有后续依赖时原样恢复；有依赖时，交给模型重新评估。

| 曾考虑的做法 | 问题 |
|---|---|
| 只允许回退最近一次 | 过严：第 12 次只改了 X，第 13 到 15 次都没有改动 X，也不能回退 |
| 依次撤回之后改过同一条目的沉淀 | 连带撤回之后的沉淀对其他条目的正确结论；被撤回沉淀的证据只能在没有原会话上下文时重做，质量下降；会覆盖学习者之后的修改，违反 2-3 |
| 回退后用剩余证据重新评估 | 实质就是重新评估，先回退这一步是多余的 |

按服务端能判断的前提分为两条路径：
1. **回退（服务端执行，原样恢复）。**前提：这次沉淀改动过的每一项（条目、学习特征、进度与待续事项、待确认事项），之后没有被任何修订再改动过。服务端查修订记录的改动清单即可判断，只涉及结构。满足时按 1.6-8 执行：从 git 取回沉淀之前的内容，相关证据变回未沉淀，生成回退记录和新的修订。
   - "只回退最近一次"是这一前提的特例。
   - 学习者修改和迁移也是修订，所以这一前提自然保护了学习者亲手改的内容（2-3），也自然阻止跨越迁移的回退（迁移前的内容是旧格式）。
   - 合并关系由未被回退的沉淀记录推导，回退后被合并的条目重新出现，证据的引用随之恢复正确。
   - 这次沉淀产生、尚未处理的待确认事项随之撤回；已被确认的，确认本身是之后的修订，会阻止回退。
2. **前提不满足时，改为重新评估。**服务端拒绝回退，列出冲突的后续修订（哪几项、被哪次操作改动）。纠正的做法：
   - 证据本身不该计入的（例如来自放弃的分支），先撤销证据；
   - 模型读取相关条目的全部未撤销证据重新评估（1.6-11），学习者手改的内容作为自述主张保留并参与判断；
   - 作为一次沉淀整体提交，沉淀记录的类型为"学习者要求"，注明针对的是哪一次沉淀。
   - 被针对的沉淀本身不被回退，它计入的证据仍算已计入；重新评估不计入分量，不变量 3 不受影响。

保留路径一，是因为最常见的情况是刚沉淀完就发现不对：回退后证据变回未沉淀，可以在本会话中带着完整的上下文和学习者的澄清重新沉淀，质量高于只依据证据的重新评估。

**新概念的登记。**1.10 规定新概念在写入证据时声明，5.1 规定证据保存解析得到的编号，所以新概念在声明时、早于任何沉淀就需要编号。声明时由服务端立即建立条目，只有名称、别名和编号，摘要为"尚未沉淀"，产生一次"登记"修订；沉淀只负责填写内容。
- 另一个会话在沉淀前使用同一名称，可以解析到它，不会再被当作未知标注拦下。
- 回退"填写内容"的沉淀时，条目回到"尚未沉淀"而不是被删除，之后证据对它的引用始终有效。证据不是修订，这种依赖不会出现在修订记录的改动清单中，路径一的前提查不出来，所以需要这样处理。
- 登记只建立名称和编号，不包含关于学习者的主张，与"状态由证据沉淀而成"不冲突。
- 曾考虑把登记放在单独的记录中、沉淀时才建文件，代价是名称解析要同时查条目文件和登记记录两处。

**标注的错误与更正。**1.10 把未知标注改为写入时拦下之后，拿不准的命名不再作为积压留下，模型必须当场决定，决定错了也不留痕迹。会出两类错误：

| 错误 | 例子 | 服务端能否发现 | 纠正 |
|---|---|---|---|
| 重复登记：把已有概念的另一种叫法声明为新概念 | 已有"中断优先级"，又登记"NVIC 优先级分组" | 判断不了重复，但能统计新登记的条目 | 回顾时合并 |
| 标错：证据标到了不对的已有条目上 | 关于优先级分组的证据标到了"中断服务函数" | 不能 | 更正标注（见下） |

原先标错没有纠正的途径：证据不可修改，撤销会把有效的证据一起丢掉。更正因此增加第三种类型"更正标注"：追加一条记录，写明某条证据的概念标注改为什么，证据索引按更正后的标注计算（与合并关系一样，由不可变的记录推导）。它和改名、合并一样调整的是组织方式（1.3-4），因此模型可以在沉淀和回顾中发起，在简报中告知；被影响的两个条目（原条目去掉这条证据的影响，新条目吸收它）与更正记录在同一次沉淀中整体提交。学习者也可以发起。这修订了 1.10 中"更正由学习者发起"。

**回顾的触发指标（修订 1.6）。**1.6 的服务端指标中"未处理的未知标注数"写于 1.10 之前；1.10 之后未知标注不再进入存储，这个指标恒为零。它原本测量的是知识地图的组织是否需要整理，改为"上次回顾以来新登记的条目数"。它与"距上次回顾的证据数"测的不是一回事：持续练习已有的概念时证据多而新条目少，组织方面的风险低；开始学新课程时新条目集中出现，重复和粒度不一致的风险高。

回顾时可以留意新登记的条目是否与已有条目重复、粒度是否一致。这属于启发层，不作约束，以免回顾过于集中在新登记的条目上；回顾的具体流程以后讨论（暂缓区）。

**代价。**
- 修订记录和 git 两份历史要保持对应：由服务端在同一次提交中生成修订记录，并在提交说明中写修订号。
- 回退依赖完整的 git 历史，数据仓库的历史不能改写。
- 学习者的本地修改以一次拉取为单位生成修订：一次推送混着几处修改时只生成一个修订，追溯的粒度粗一些。
- 运行数据丢失时会重复告知一次增量。

**按约束力整理。**

| 层次 | 内容 |
|---|---|
| 硬约束 | 修订号全局递增，修订记录不可变，与提交通过修订号对应；记录文件只能追加，拉取后校验；回退的前提由服务端检查，不满足时拒绝；改动状态或设定的写入先拉取、写入后立即推送，冲突时放弃并报告；声明新概念时登记为条目 |
| 约定 | 纠正较早的沉淀用"学习者要求"的重新评估；更正标注在简报中告知 |
| 目标 | 历史可追溯、可撤回；不覆盖学习者的修改 |
| 启发 | 回顾时可以留意新登记的条目；声明新概念前先在知识地图中找能覆盖它的已有条目（议题 6） |

**结论。**

| 编号 | 结论 |
|---|---|
| 5.2-1 | 修订记录是逻辑历史；git 是物理历史，负责内容存档、备份和同步。不用提交编号引用，提交说明中写修订号 |
| 5.2-2 | "状态版本"改称"修订"，覆盖设定和状态（含待确认事项）的每一次变化；"版本"只用于软件和格式 |
| 5.2-3 | 学习者的本地修改在拉取后生成"学习者修改"修订并做结构检查；记录文件只能追加，已有的行被改动时从 git 恢复并报告 |
| 5.2-4 | 会话已知的修订作为运行数据，不进 git；最后写入时间由证据推导；会话记录不可变（修订 1.10） |
| 5.2-5 | 每次写入在本地提交；证据追加在后台推送；改动状态或设定的写入先拉取、立即推送；数据仓库不改写历史 |
| 5.2-6 | 回退有前提（之后没有修订改动过同一项）：满足时原样恢复；不满足时拒绝，改为"学习者要求"的重新评估；不做连带撤回（细化 1.6-8） |
| 5.2-7 | 声明新概念时由服务端登记为条目（名称、别名、编号，摘要"尚未沉淀"），沉淀只填写内容 |
| 5.2-8 | 更正增加"更正标注"，模型可在沉淀和回顾中发起，在简报中告知，与相关条目的修改整体提交（修订 1.10） |
| 5.2-9 | 回顾的服务端指标"未处理的未知标注数"改为"上次回顾以来新登记的条目数"；留意新登记的条目属于启发，不作约束（修订 1.6） |
| 5.2-10 | D8 的观察项增加"登记的条目后来被合并的比例"和"标注更正的次数"；"声明新概念前先在知识地图中找能覆盖它的已有条目"作为议题 6 的启发层输入 |

#### 5.2-B 版本与迁移（已定）

**要解决的问题。**
1. 插件（技能文本和钩子）、服务端、数据格式三者都会变化。
2. 三者不能同时更新：插件分别安装在 Claude 和 ChatGPT 两个平台，由学习者手动更新；服务端由 Codex 部署；已打开的对话中保留着开场时加载的技能文本，插件更新不会改变进行中的对话。不一致的窗口必然存在。D1 规定不做新旧混用的兼容，所以要能发现不一致、明确拒绝、说明该更新哪一方。
3. 数据格式改变时需要迁移：分哪几类、由谁执行、怎样验证、失败怎样恢复。
4. DESIGN.md 中现行的迁移约定（FORMAT_VERSION 不一致时拒绝启动、迁移脚本可以重复运行、回滚时退回数据仓库）需要按新设计重新审视：状态不能廉价地重建，有了修订，git 的规则已在 5.2-A 中确定。

**两个编号。**

| 编号 | 覆盖 | 何时改变 |
|---|---|---|
| 发布版本 | 插件和服务端共用 | 每次发布 |
| 数据格式版本 | 沿用 FORMAT_VERSION，整数 | 只在存储格式改变时加一 |

插件和服务端在同一个仓库中开发、一起构建和发布，共用一个编号就不需要对照表；版本号的写法在议题 10 决定。数据格式很少变化，迁移按"从 N 升到 N+1"逐步串联，因此单独编号；每个服务端版本声明它支持的数据格式版本（与现行做法相同）。

**插件与服务端的一致性：服务端规定可接受的范围。**

| | 严格一致 | 可接受的范围（采用） |
|---|---|---|
| 规则 | 插件版本必须等于服务端版本 | 插件版本不低于最低插件版本，且不高于服务端版本 |
| 只改服务端的修复 | 两个平台的插件都要更新 | 插件不用动 |
| 插件比服务端新 | 拒绝 | 拒绝 |
| 复杂度 | 最低 | 多一个由开发者维护的数字 |

最低插件版本只在技能与工具之间的接口改变时提高：工具的名称、参数或含义改变；技能中描述的记录或状态格式改变；新增需要技能配合才能成立的硬约束。是否提高由开发者在发布时判断，列入议题 10 的发布检查清单。

采用范围的理由：试跑期间会有频繁的只改服务端的修复，严格一致要求每次都在两个平台更新插件。范围只是一道门，不引入任何兼容代码：技能文本不会与它不认识的接口一起运行，与 D1 一致。

**怎样发现不一致。**
- 构建插件时把插件版本写进技能文本。
- 开场加载的工具有必填参数"插件版本"，模型从技能文本中照抄。
- 服务端比较：
  - 缺失：说明没有通过插件使用，提示需要通过 Cairn 插件使用（D1）。
  - 超出范围：拒绝加载，说明该更新哪一方。插件过旧时提示更新插件；插件比服务端新时提示服务端尚未部署到这个版本。
  - 在范围内：正常加载，插件版本记入会话记录（会话记录不可变，5.2-A，插件版本在创建时写入）。
- 升级前已打开的会话：每次工具调用带有会话标记，服务端由此知道该会话的插件版本；它已低于新的最低插件版本时，拒绝调用并提示开启新会话。旧会话未沉淀的证据按 1.6-5 由新会话代为沉淀，不会丢失。
- 比较由服务端执行：结果确定，可以强制；由模型比较既不可靠，也无法强制。

**部署顺序。**接口改变时，先部署服务端（含迁移），再更新两个平台的插件。中间这段时间用旧插件开场会被拒绝，并提示更新插件；窗口很短，时机由学习者掌握。反过来先更新插件也可以，只是提示的是"服务端尚未部署"，不如前者直接。

**迁移的分类。**

| 数据 | 格式改变时 | 由谁执行 |
|---|---|---|
| 记录（JSON Lines） | 机械迁移 | 脚本 |
| 状态的结构化开头 | 机械迁移 | 脚本 |
| 状态的正文（摘要、详情） | 服务端不解析正文；需要理解内容的变化只能由模型完成 | 模型 |
| 设定（profile/settings/） | 条目的结构化开头机械迁移；学习者自由写的文件不迁移；位置变化时机械移动 | 脚本 |
| 派生数据 | 删除重建 | 服务端 |
| 运行数据 | 丢弃，按 5.2-A 的保守方式恢复 | 服务端 |

由此分为三类：
1. **机械迁移：**由脚本改动结构，结果确定。
2. **模型补全：**需要理解内容的变化，例如 1.2-4 中"从摘要中提取机器可读的状态等级"。先用机械迁移把结构改好，新字段允许缺省，新格式在模型补全之前就是合法的；之后由模型在沉淀或回顾中逐步补全，必要时安排一次专门的回顾；服务端可以统计缺少新字段的条目数（事实性指标）。这样部署不依赖一次长时间的模型运行，补全也沿用现有的沉淀流程（整体提交、产生修订）。代价是使用新字段的功能要能处理缺省的情况。
3. **重放（D7）：**改进推断方法后对全部证据重新沉淀。这是有意识的选择，不是常规的迁移途径。

**状态在迁移上按原件对待。**DESIGN.md 把 concepts.md 列为"派生数据，可以从 log 重建"，交接文档中也写过"状态可由证据重新评估生成"。原则上状态由证据派生（D7），但重建需要模型对全部证据重新沉淀：成本高，原会话的上下文已不在，结果可能不如原来的沉淀。因此迁移时迁移状态，而不是重建它。

**机械迁移的执行。**
- **位置：**系统仓库的服务端代码中。每个脚本把数据格式从 N 升到 N+1，附带测试数据；同一次提交中提高服务端支持的数据格式版本（沿用现行约定）。
- **时机：**部署时用管理命令显式执行，不在服务启动时自动执行。迁移改写的是唯一的一份真实数据，自动执行意味着一个有问题的提交会在无人查看时改写数据。服务端启动时数据格式版本不一致就拒绝启动，并说明原因：数据较旧时提示先执行迁移；数据较新时提示代码版本不对。
- **步骤：**
  1. 演练：在数据仓库的临时副本上执行，输出检查结果和改动统计，不触及真实数据。
  2. 执行：停止服务；确认数据仓库干净且已推送（包括后台推送的证据）；打上迁移前的标签；依次执行脚本。
  3. 检查：服务端对全部数据做结构检查（见下）。
  4. 通过：作为一次提交，产生一个"迁移"修订，改动清单包含所有受影响的条目，因此回退不会跨越迁移（5.2-A）；推送，启动服务。
  5. 不通过：放弃全部改动，回到迁移前的标签。
- **检查内容（结构性，服务端可以完成）：**每行记录都能解析；证据的条数和编号集合与迁移前一致；编号唯一；所有引用（证据指向条目、沉淀记录指向证据、并入关系）都能解析；每个条目的结构化开头合法；数据格式版本正确。各脚本可以加上自己的检查。
- **脚本不必幂等：**由执行器保证"要么全部完成并提交，要么回到迁移前"。这比要求每个脚本可以重复运行更简单，也更可靠。修订 DESIGN.md 中"迁移脚本可以重复运行"。

**回滚。**
- 迁移后还没有新的写入：可以退回迁移前的标签，并把系统部署回旧版本。
- 已经有新的写入：退回会丢掉新的证据，因此不退回，改为写一个修复迁移向前修正。迁移提交之后是否有新的提交，服务端可以判断。
- 改变接口的发布：回滚时两个平台的插件也要退回，因此这类发布以向前修正为主。

**代价。**
- 开场加载多一个参数；照抄的是确定的字符串，出错的风险低。
- 改变接口的发布要先在两个平台更新插件，才能继续学习。
- 升级时正在进行的对话要换到新会话，旧对话中尚未记录为证据的内容不会带过去；改变接口的部署宜放在不学习的时候。
- 部署多一步显式的迁移，由 Codex 按部署流程执行。
- 模型补全的新字段在一段时间内不完整。

**与已定结论的关系。**与 D1 一致：只设门槛，不做兼容。与 5.2-A 一致：迁移产生修订，回退不跨越迁移；数据仓库的历史不改写，只在没有新写入时退回。暂缓区中早期插件草案的"协作说明的版本核对"由本节的插件版本检查覆盖。讨论结束、结论并入 DESIGN.md 时，"演进与迁移"一节按本节重写（状态的定位、脚本是否幂等、回滚规则）。

**按约束力整理。**

| 层次 | 内容 |
|---|---|
| 硬约束 | 开场加载必须带插件版本，服务端按可接受的范围检查，不在范围内时拒绝；会话记录保存插件版本，低于最低插件版本的会话的调用被拒绝；数据格式版本与服务端支持的不一致时拒绝启动；迁移整体完成或全部放弃；迁移产生"迁移"修订 |
| 约定 | 接口改变时提高最低插件版本；先部署服务端，再更新插件；迁移用管理命令显式执行，先演练；迁移后已有新写入时向前修正 |
| 目标 | 技能文本不会与它不认识的接口一起运行；数据在迁移中不丢失，结果可以验证 |
| 启发 | 改变接口的部署放在不学习的时候 |

**结论。**

| 编号 | 结论 |
|---|---|
| 5.2-11 | 两个编号：插件与服务端共用发布版本，数据格式版本单独编号 |
| 5.2-12 | 服务端规定可接受的插件版本范围（最低插件版本到服务端版本）；最低插件版本只在技能与工具之间的接口改变时提高 |
| 5.2-13 | 开场加载必须带插件版本，缺失或超出范围时拒绝并说明更新哪一方；会话记录保存插件版本；升级后低于最低插件版本的会话的调用被拒绝，提示开启新会话 |
| 5.2-14 | 接口改变时先部署服务端，再更新插件 |
| 5.2-15 | 迁移分为机械迁移、模型补全、重放三类；状态在迁移上按原件对待；新格式在模型补全之前必须合法 |
| 5.2-16 | 机械迁移用管理命令显式执行：演练、执行、检查、一次提交（产生"迁移"修订），失败时回到迁移前；脚本不必幂等，由执行器保证整体性 |
| 5.2-17 | 迁移后没有新写入时才退回，否则向前修正；改变接口的发布以向前修正为主 |

#### 5.2-C 目录布局与初始化（已定）

**要解决的问题。**
1. 5.1 定了各类数据的形态，5.2-A、5.2-B 增加了修订、登记、运行数据、插件版本，需要把它们放到具体的文件和目录中。
2. 系统尚未运行过，没有历史数据；首次迁移等全部讨论结束后再做。
3. 讨论中发现"profile"一词的含义一路漂移，"关于学习者本人"的内容被按权威拆在两处，需要重新定义（见下文"关于学习者本人的内容"）。

**布局要满足的要求。**
1. 看路径就知道谁能改，服务端按目录执行修改规则。
2. 数据仓库可以直接作为 Obsidian 库打开（5.1）。
3. 服务端只读结构化开头，不解析正文：凡是要逐项追踪的东西（修订的改动清单、回退的前提、待确认的状态变更、统计指标），每一项都有自己的文件或结构化字段。
4. 不进 git 的东西不放在仓库中。

**布局。**

```
cairn-data/
├── FORMAT_VERSION                数据格式版本，新格式从 2 开始
├── README.md                     给学习者的说明：各目录是什么、谁来写
├── AGENTS.md / CLAUDE.md         本地 agent 的入口（内容在议题 8）
├── DEPLOYMENT.md                 实例信息（沿用）
├── .gitignore                    sources/、/notes/、/.obsidian/
├── profile/                      关于学习者本人的内容
│   ├── settings/                 学习者设定：只在学习者说出或确认设定建议后修改，沉淀和回顾不能改
│   │   ├── <名称>.md              每条一个文件，写明做什么、为什么
│   │   ├── resources/<资源名>.md  各资源的学习目的
│   │   └── 学习者自由写的文件      没有结构化开头，模型只读
│   └── descriptions/             关于学习者本人的描述：背景、学习特征；由沉淀和回顾维护
│       └── <名称>.md              每条一个文件，条目结构
├── state/
│   ├── concepts/<正式名称>.md     知识掌握，每个条目一个文件（含登记的条目）
│   └── progress/<资源名>.md       进度（内部结构在议题 9 定）
├── records/                      只能追加，只有服务端写
│   ├── evidence/<开始时间>-<会话编号>.jsonl
│   ├── sessions.jsonl  corrections.jsonl  consolidations.jsonl
│   ├── reverts.jsonl   revisions.jsonl
│   └── pending.jsonl             待确认的状态变更与设定建议，以及处理结果
└── sources/                      材料（Syncthing 同步，不进 git）
（仓库之外：服务器本地的派生数据和运行数据目录）
```

**各部分的说明。**
1. **第一层按性质分。**profile/（关于学习者本人的内容）、state/（知识掌握、进度）、records/（记录）、sources/（材料）。修改规则跟着路径走：records/ 只能追加（5.2-3）；profile/settings/ 不受沉淀和回顾的改动；profile/descriptions/ 和 state/ 由沉淀维护；profile/ 和 state/ 的本地修改生成"学习者修改"修订；sources/ 不归 git 管。
2. **records/。**证据每个会话一个文件，命名为"开始时间-会话编号"，按名称排序就是时间顺序（会话编号与会话标记的关系在议题 7 定）。其他记录每种一个文件，暂不按月拆分：两年内证据总量只有几 MB，过大时再做一次机械迁移（5.1-4）。待确认的状态变更和设定建议放在同一个文件里，用类型字段区分，两个术语照样分开；它们的处理结果追加在同一个文件中，提议的内容在确认前存在记录里，确认后才写入。
3. **state/。**concepts/ 每个条目一个文件（含登记的条目，5.2-7）；progress/ 每个资源一个文件，内部结构在议题 9 定。待续事项放在哪里也在议题 9 定，约束是：服务端必须能统计未处理的待续事项的数量和时长，因为 1.6 的回顾指标要用。
4. **派生数据和运行数据放在仓库之外**，存放在服务器本地的目录，路径由服务端配置决定。这样仓库里的东西要么归 git 管，要么由 Syncthing 同步；删除缓存永远不会触及仓库；不会被误提交；学习者本地的副本中不会出现服务端的缓存。
5. **Obsidian。**以仓库根目录作为库，这样关于学习者本人的描述中的 `[[ ]]` 也能链接到 state/concepts/ 中的概念。Obsidian 按文件名解析链接，所以文件名在 profile/ 和 state/ 范围内不能重复，写入时由服务端检查。条目开头的别名字段命名为 `aliases`，Obsidian 可以识别它。.gitignore 排除根目录的 .obsidian/（学习者个人的界面配置）。详情中的链接怎样写，在议题 6、7 定。
6. **命名。**目录名和记录文件名用英文，与术语表中的英文标识一致；条目文件名用正式名称，可以是中文（5.1-3）；资源名沿用现在的写法。

**存放按性质，呈现按相关。**文件放在哪里，决定谁能改、改动怎样追踪；模型在上下文中看到什么，由服务端开场时的拼接决定（DESIGN.md 原则 12："磁盘上怎么分文件，模型看不到"）。每次会话都要用的内容，全部放进开场加载的结果，不会漏读，也不增加工具调用（0.4 总原则）。例如各资源的学习目的存放在 profile/settings/resources/ 下，拼接时和这个资源的进度放在一起呈现。

**关于学习者本人的内容（profile）。**

"profile"一词的含义变化：

| 阶段 | profile 指什么 | 谁写 |
|---|---|---|
| 重构前第一版 | 背景、目标、偏好 | 学习者；模型只读 |
| 0.3 | 同上，模型可以修改，但学习者须知情 | 学习者和模型 |
| 议题 2 | 只存放学习者设定，背景移入状态 | 学习者；模型在学习者要求或确认后写 |
| 5.2-C | 关于学习者本人的内容：学习者设定，加上关于学习者本人的描述（背景、学习特征） | 设定：学习者；描述：沉淀和回顾 |

问题：议题 2 按权威分目录，指令一处、描述一处，"关于学习者本人"这一主题被拆散；名称和内容对不上（profile/ 里装的是指令）；学习者最初的设想——模型在教学中逐渐形成"怎样教这个学习者"的认识，并不断细化——失去了完整的位置。其中混着三个问题：权威（指令还是描述，议题 2 已解决，保留）；谁来写；怎样组织。

*沉淀和回顾能否修改。*

| | S1 必须确认（原 2-2） | S2 知情即可 | S3 按每条的性质（采用） |
|---|---|---|---|
| 规则 | 设定只在学习者说出或确认后修改；推断进入学习特征 | 沉淀和回顾可以直接改设定，在简报中告知，学习者可以撤销 | 学习者的指令只有学习者能改；模型推断出的教法作为描述，沉淀和回顾可以直接改，告知学习者，重大变更待确认 |
| 误判被固定的风险 | 无 | 有 | 无 |
| 学习者的原话会不会被冲淡 | 不会 | 会 | 不会 |
| 学习者要做的确认 | 设定建议都要确认 | 最少 | 只有重大变更要确认 |

不让推断直接成为指令，是因为一个具体的风险：模型推断出"喜欢例子"，如果写成指令"多用例子"，以后每次都照做，再也得不到其他讲法效果的证据，这条推断即使错了也没有机会被推翻，因为指令只照做、不接受证据检验。写成描述时，模型照样多用例子，但仍然会偶尔试别的讲法，证据可以修正判断。S3 既满足"对教法的认识随教学自动细化并直接影响教学"，又避开了这个风险。0.3 中学习者最初的立场是"知情即可"，议题 2 收紧为"必须确认"；S3 对描述采用知情加重大变更确认，对指令保持必须确认。

*profile 的定义。*P-A：profile 只存放设定（议题 2 的定义），背景和学习特征在 state/；P-B（采用）：profile 是关于学习者本人的内容，包括设定和关于学习者本人的描述，知识掌握和进度仍在 state/。P-B 让名称和内容一致，"怎样教这个学习者"的指令和描述都在同一个主题下，沉淀和回顾可以修改其中的描述部分，符合学习者最初的设想，同时保留了议题 2 最关键的指令和描述之分。

*用两个子目录表达性质。*

| | 一个目录，用字段区分 | 两个子目录（采用） |
|---|---|---|
| 一眼看出性质 | 要打开文件看开头 | 看路径就知道哪些是学习者说的、哪些是模型的判断 |
| 服务端执行修改规则 | 读字段 | 按目录，与 records/ 整个目录只能追加是同一种做法 |
| 性质被意外改变 | 在 Obsidian 中改字段时，可能悄悄把描述变成指令 | 要把文件移到另一个目录，动作明确，服务端能检测到 |
| 学习者自由写的文件 | 与模型写的条目混在一起 | 自然地放在设定一边 |

性质只用目录表达，不另设字段，以免出现两个可能互相矛盾的信息来源。"沉淀和回顾不能改设定"因此成为硬约束：沉淀和回顾提交的改动不能触及 settings/，设定只能通过单独的"设定修改"操作改变。命名用 descriptions/ 而不用 traits/，因为其中除了学习特征还有背景条目。

*每条一个文件。*曾考虑过把关于学习者本人的描述写成一份由模型自由组织的综合文档（画像），综合性强、文件少，但追踪粒度粗，改一处整份都算改动。采用每条一个文件，理由是：每条有自己的历史，git 中可以单独查看，修订、回退、待确认的变更都能精确到这一条；沿用知识掌握条目的机制（先粗后细、合并、拆分、登记、别名，1.3），不需要设计新机制；不预设分类，喜好、效果等类型只作为启发（1.4），条目怎样划分由模型按"教学决策是否不同"（1.3-1）判断；整体视图由服务端拼接各条的摘要提供，不需要另外维护综合文档。学习者认为学习中的特征很多，怎样推断、验证、组织难以预先规划，而且模型会不断变化；这里没有规定推断和分类的方式，留给模型和精简的启发。

*规则。*
1. **学习者设定（profile/settings/）。**只在学习者说出或确认设定建议后修改，通过单独的"设定修改"操作；沉淀和回顾提交的改动不能触及 settings/（硬约束）。每条一个文件，写明做什么、为什么，不带日期：会话中刚说出的指令一定比文件中的新，"较新的优先"（议题 2）不需要日期也能执行；文件内部的要求互相矛盾时由模型指出，学习者决定；需要追溯时间时查修订和 git。写明理由，是为了让指令写在"合适的高度"（Anthropic 的提示建议），模型能据理由推广。各资源的学习目的放在 settings/resources/<资源名>.md。学习者自由写的文件没有结构化开头，模型只读，视为学习者的指令；学习者明确要求时才修改。这修订了议题 2 中"profile/ 自由组织"的约定。
2. **关于学习者本人的描述（profile/descriptions/）。**背景和学习特征，每条一个文件，沿用条目结构（2-4）。由沉淀和回顾维护，重大变更待确认，每次在简报中告知；学习者可以直接修改，来源记为自述。
3. 服务端区分条目和学习者自由写的文件：有结构化开头的是条目，由服务端管理。
4. 设定建议被接受时，在 settings/ 新建一条指令，descriptions/ 中原来的描述保留（2-8）。学习者在 Obsidian 中把一条描述直接移入 settings/ 时，按"学习者修改"处理，格式不合要求时报告。
5. 开场拼接的顺序：协作说明 → 学习者设定 → 关于学习者本人的描述 → 知识掌握 → 进度（细化 2-6）。

*术语。*学习者设定和学习者状态的含义不变，只是存放位置：设定在 profile/settings/；状态中关于学习者本人的部分（背景、学习特征）在 profile/descriptions/，知识掌握和进度与待续事项在 state/。"描述"作为性质（与"指令"相对）覆盖整个学习者状态；descriptions/ 只存放其中关于学习者本人的部分，知识掌握和进度分别按概念和资源组织，放在 state/。为避免混淆，后者的正式术语为"关于学习者本人的描述"。

**背景与知识掌握的分界。**涉及具体知识的自述（"上学期学过数据结构"），作为自述证据标注到相关概念上，进入知识掌握；背景只记不属于任何条目的情况：学科背景、经历、使用的工具和环境、能投入多少时间。这样同一件事不会记在两处（议题 2 中"作为自述主张写入状态"的例子相应细化）。

**学习特征的边界。**学习特征只描述学习上的行为，不推断健康、情绪或性格；疲惫、赶时间这类临时状态仍然只作为证据的情境（0.3-5）。平台记忆明确不记这类推断；学习特征本身就是推断，更需要这条边界。1.4 已有"主张写成可观察的行为"，这条补全了范围（补入 1.4 的约定）。

**条目结构。**保留：结构化开头（稳定编号、正式名称、别名）、摘要、详情；证据索引由服务端计算，不写进文件。结构化开头由服务端管理，模型不直接写；改名、合并、拆分走专门的操作（1.3）。
- 好处：每个条目可以单独定位，修订、增量、回退的前提、冲突检测、证据索引都以它为单位；摘要组成知识地图，支持以后只送地图、详情按需读取；结构化字段和自由文本分工，与 Anthropic"状态数据用结构化格式，进展笔记用自由文本"的建议一致；模型用名称、服务端用编号，Anthropic 指出模型处理有语义的名称比处理晦涩的编号准确得多；学习者可以直接阅读和修改，git 差异按条目显示。
- 代价：文件多，整体视图靠服务端拼接；结构化开头可能被写坏（Anthropic 观察到模型容易不当修改或整体覆盖 Markdown 文件），所以由服务端管理和校验；详情变长后整条重写成本高，靠 1.5-3 的压缩约定和条目大小上限控制；摘要和详情可能不一致，约定沉淀时两者一起检查。
- 修改的复杂度由工具承担（议题 7 的输入见下文）。不把条目改成 JSON：Anthropic 关于 JSON 的结论针对的是状态字段，条目正文是带推理的判断，用 JSON 书写和阅读都会变差。

**初始化（原"首次迁移"）。**系统尚未运行，没有历史数据：
- 不写从格式 1 到格式 2 的迁移脚本，用新模板初始化数据仓库；
- 数据格式版本从 2 开始，不复用 1，新服务端遇到旧仓库会拒绝启动，避免误读旧结构；
- 沿用现有的 cairn-data 仓库，用一次提交换上新结构，旧内容留在 git 历史中，服务器路径、认证、Syncthing 配置都不用动；
- 设定和背景以后再写，背景也可以在第一次会话中作为自述记录（冷启动，议题 4）；
- 在议题 10、全部讨论结束后执行。

**迁移执行器与结构检查。**5.2-B 的迁移管理命令推迟到第一次需要改格式时实现，与 DESIGN.md 现行的安排一致；其中的结构检查从第一版就实现，用于服务端启动时、学习者推送修改后和单独的管理命令，以后迁移直接复用。

**讨论中提出、记给后续议题的输入。**
- **规模增长后的送入方向（暂缓区，议题 3）：**定为"常驻知识地图，详情按需读取"，替换原来的三阶段设想；现阶段仍整份送入（D5）。相关性只有模型能判断（1.5），让模型根据知识地图选择要读的详情；摘要已包含待验证之处、已知误解和跨主题关联的提示（1.5-2），足以引导读取；漏读的风险用读取规则约束，例如深入讲解一个条目或判定缺口之前，必须先读它的详情。这与 Claude 平台记忆、Agent Skills 的渐进加载是同一思路，不改变数据结构（1.5-5）。
- **与平台记忆的分工（议题 3）：**学习者在 claude.ai 或 ChatGPT 上使用 Cairn 时，平台记忆和 Cairn 的状态会同时进入上下文，内容有重叠。学习相关的状态和设定以 Cairn 为准，因为它有证据、时间和置信程度；平台记忆中与 Cairn 不一致的学习内容，视为可能过时的自述；Cairn 不写平台记忆；冷启动时参考平台记忆，只作为线索，经学习者确认后记为自述证据并注明来源。
- **议题 7：**用名称指定条目，别名也能解析；摘要整段替换，详情支持局部替换、追加和整段重写；一次沉淀的多处修改用一次调用、整体提交；工具结果返回改动前后的差异；报错给出可行的修正（如相近的名称）；沉淀因修订过时被拒绝时，同时返回期间的增量，模型合并后再提交；条目大小上限（与 1.5-4 的关系届时再定）。这与 Anthropic 关于写工具的建议一致：合并操作、使用有语义的名称、给出可行的报错。
- **议题 8：**代为沉淀时，客户端有对话检索能力的，检索原会话补充上下文；agent 客户端的钩子可以读取对话记录。都属于增强，按 D4 根据工具列表判断。

**参考：平台记忆与 Cairn 的对照。**讨论中对照了 Claude 和 ChatGPT 的平台记忆。Claude 的记忆按主题分文件（你是谁、希望怎样被对待、各领域的事实、进行中的事、相关的人），只记用户亲口说过的内容，在每一轮结束后由后台整理，常驻层加目录、详情按需读取，用版本号防止并发冲突；ChatGPT 有保存的记忆、引用聊天记录和持续更新的记忆摘要。最根本的区别是：平台拥有完整的对话记录，可以事后整理；Cairn 只是一个工具服务，只能看到模型通过工具交给它的内容，所以证据只能由会话中的模型当场记录（0.2-5）。Cairn 的三层大致对应三种记忆：证据是情景记忆，状态是语义记忆，技能和设定是程序性记忆；平台记忆基本只有语义一层，Cairn 的优势在证据层。印证已定设计的两点：Claude 记忆"新建文件前先查有没有别名对得上的已有文件"，与议题 6 的启发"声明新概念前先在知识地图中找"相同；Claude 记忆从对话结束后总结改为边聊边记，与 1.6 不依赖会话结束的决定一致。不照搬的三点：只记自述（Cairn 的价值在推断）；一行一个事实（详情需要写出来龙去脉）；不保存原始记录。

## 3D. 议题 3：开场与上下文供给（已定）

要回答的是：每次会话开始时，模型的上下文中应该有什么、按什么顺序、通过什么途径送达，怎样保证送到、看到；数据增长后怎样控制体积；会话中途上下文被压缩后怎样恢复。分三轮：3-A 开场；3-B 体积与增长；3-C 会话中途（压缩后的恢复、增量、去重）。与平台记忆的分工（5.2-34）并入 3-A。

### 3-A 开场：送什么、怎样送（已定）

**要解决的问题。**
1. 开场时上下文中有哪些来源，哪些能控制。
2. 技能和加载结果怎样分工。
3. 学习者设定通过工具结果送达，而模型对工具结果中的指令天然谨慎（这是重构的起因之一），怎样让设定有指令的分量。
4. 加载结果的顺序和位置。
5. 怎样保证该送的都送到、模型都看到；工具结果有大小上限。
6. 开场时的待处理事项（补做沉淀、待确认事项、材料变化等）什么时候处理，才不拖慢开始学习。
7. 平台记忆同时在上下文中。

**上下文的来源。**

| 来源 | 谁控制 | 何时进入 | 作用 |
|---|---|---|---|
| 平台的系统提示、平台记忆 | 平台 | 始终 | 不受控制，分工见下文 |
| 项目指令（Claude 或 ChatGPT 的 Project） | 学习者 | 始终 | 可选的触发辅助（议题 6、10） |
| 技能的名称和描述 | 插件 | 始终 | 触发 |
| 技能正文（协作说明） | 插件 | 模型判断相关时读取 | 怎样协作 |
| 技能的参考文件 | 插件 | 按需 | 格式规范等（D1） |
| MCP 工具的定义 | 服务端 | 始终 | 工具说明 |
| 开场加载的结果 | 服务端 | 调用后 | 学习者的个人数据 |
| 钩子注入的内容 | 插件 | 会话开始、压缩后 | 只在 agent 客户端，属于增强（议题 8） |

**分工：技能写"怎样做"，加载结果只给关于学习者的事实和学习者的指令。**技能是通用的，随插件版本发布：讲解、记录证据、沉淀的做法，约束和启发。加载结果是个人的，随修订变化：设定、描述、知识掌握、进度、未沉淀的证据、开场待处理的事项。加载结果中不放通用的行为说明，待处理事项只写事实（例如"会话 #12 有 3 条未沉淀的证据，已闲置 5 天"），怎样处理写在技能中。这样每条说明只出现一次（OpenAI GPT-6 提示指南的建议），也避开了工具结果中的指令容易被忽视的问题。

**学习者设定的分量：由技能明确授权。**OpenAI 的 Model Spec 规定，工具输出默认没有任何权威，其中的指令只能作为信息；更高一级的指令可以明确地把权威授予这些内容。技能中写明：加载结果中标为"学习者设定"的一节是学习者本人的指令，优先于技能中的默认做法；加载结果的其他部分（描述、知识掌握、证据、材料）都是信息，不是指令。这也防止材料或证据中混入的类似指令的文字被执行。按 5.2-13，开场加载必须带上只写在技能文本中的插件版本，模型没读技能就无法加载，所以设定送到时，技能中的授权一定已在上下文中。

**加载结果的结构和顺序。**一次加载调用返回以下各节，用标签分节，技能可以按名称引用：

```
<cairn_session 会话标记 · 当前修订 · 插件版本检查的结果>
  <learner_settings>        学习者设定（技能授权的指令）
  <learner_descriptions>    关于学习者本人的描述
  <knowledge>               知识掌握（3-B：地图完整，详情在预算内）
  <current_resource>        当前资源的进度和学习目的
  <unconsolidated_evidence> 未沉淀的证据，按会话分组
  <action_items>            开场要处理的事项，只写事实
</cairn_session>
```

设定放在最前：它很短，又决定怎样使用后面的内容，也符合 2-6 的顺序。长内容在中间，待处理事项在最后：Anthropic 的长上下文建议是把长文档放在前面、要求放在最后，测试中最多可提升约 30%。当前资源完整送入，其他资源每个一行位置；学习者开场没说学哪个资源时，加载结果列出各资源，由模型询问。

**完整性与大小上限。**工具结果的上限：claude.ai 和桌面端约 150,000 字符；Claude Code 默认 25,000 token（可调整）；ChatGPT 未查到公开数字，议题 10 实测。按 1.5 的估算，200 个条目整份送入约 6 万到 10 万 token，这学期就会接近 claude.ai 的上限，在 Claude Code 中几十个条目就会超出默认上限；只送摘要时 200 个条目约 1 万 token。因此加载从第一版起支持分段：
- 必需部分保证放得下（3-B 的表）；放不下的内容分段送达，必需部分写明共有几段，每段末尾标明"第 k/n 段"。
- 服务端从 MCP 连接得知客户端名称（1.10-4），按该客户端的上限留出余量来切分。
- 服务端记录每个会话取了哪几段；必需段落没取完之前，写入工具拒绝，报错写明"请先取第 2/3 段"。这是 0.4 总原则"约束输入的完整性"的结构化落实。

**开场时的待处理事项：不挡住开始学习。**

| 事项 | 什么时候处理 |
|---|---|
| 插件版本不符 | 阻止加载，提示更新哪一方（5.2-13） |
| 补做沉淀、代为沉淀 | 不放在开始学习之前。未沉淀的证据已在上下文中，教学可以参考；在第一个自然停顿或结束时处理；agent 客户端可以一开始就交给子代理并行处理（议题 8） |
| 待确认事项 | 列出，由模型择机提出（重提的时机在议题 4） |
| 材料变化 | 与今天的资源有关时先处理登记，其余列出（议题 9） |
| 回顾信号 | 学习结束后（1.6-6） |

开场概况控制在一两句话：现在学到哪里，有什么需要学习者决定的事，不逐条念清单（学习者希望不要过度流程化）。具体内容在议题 4。

**与平台记忆的分工（5.2-34 的落地）。**写进技能的规则：平台记忆中可能有学习相关的内容；学习相关的状态和设定以 Cairn 为准；与 Cairn 不一致的内容视为可能过时的自述，相关时向学习者提一句；Cairn 不写平台记忆。冷启动时加载结果标明"还没有关于学习者本人的描述"，模型可以把平台记忆中的内容当作线索，向学习者确认后作为自述证据记录，注明来源为平台记忆。

**开场的触发。**会话标记只能通过加载获得，写入都需要它，所以不加载就无法写入（1.6-4）。技能能否可靠地被触发，取决于技能描述和可选的项目指令（议题 6、10）。

**代价。**授权依赖技能，插件版本检查保证技能在场；分段会让 Claude Code 开场时多几次工具调用；必需段落没取完就拒绝写入，分段估算不准时会有摩擦，需要留余量并实测；加载结果中不放通用说明，技能的质量更关键（议题 6）。

### 3-B 体积与增长（已定）

**要解决的问题。**
1. 整份送入很快会撑不住：200 个条目约 6 万到 10 万 token，这学期就会达到；工具结果又有上限（3-A）。
2. 上下文要留给学习本身：一次会话中讲义 PDF 可能就有一两万 token，再加上讨论；加载越大，注意力越分散，压缩也越早。
3. 5.2-33 只定了方向（常驻知识地图，详情按需读取），没有定何时切换、预算多大、模型什么时候必须读取详情。
4. 漏读的风险：相关性只有模型能判断（1.5）。

**三种做法。**

| | A. 整份送入，达到阈值再切换 | B. 从第一天起只送地图，详情按需读取 | C. 地图始终完整，详情在预算内尽量多给，其余按需读取（采用） |
|---|---|---|---|
| 数据少时 | 详情全有，不会漏读 | 每次都要读取，完全依赖摘要质量 | 预算放得下全部详情，等于 A |
| 数据多时 | 达到阈值时行为突变，技能要写两套说明 | 不变 | 平滑过渡：放得下的给详情，其余只给摘要 |
| 实现 | 两条路径加一个开关 | 一条路径 | 一条路径，没有切换的时刻 |
| 试跑能否检验最终行为 | 要等切换以后 | 能 | 能：读取规则从第一天起就在技能中，早期很少用到 |

采用 C：D5 成为它的特例（预算够大时详情全部送入）；没有切换的时刻，技能只需一套说明，符合 D4"减少分支"；行为随数据增长平滑变化；暂缓区中"体积接近预算时再决定"一项不再需要。

**加载结果中各部分的待遇。**

| 部分 | 待遇 |
|---|---|
| 学习者设定、关于学习者本人的描述、当前资源的进度和学习目的、待处理事项 | 必需，完整送入，不截断 |
| 知识地图（所有条目的名称和摘要） | 必需，完整送入，保证覆盖完整（1.5 完整性的两个维度之一） |
| 知识掌握的详情 | 有预算：按优先级填充，填满为止 |
| 未沉淀的证据 | 有预算：超出时给出各会话的条数和最近的若干条，并把补做沉淀列为首要的待处理事项 |

必需部分本身超出客户端上限时，按 3-A 分段送达。

**详情的填充顺序。**只用结构性信号，只决定先给谁详情，不决定给谁看（所有条目都在地图中）：
1. 有未沉淀证据的条目（沉淀时要用）；
2. 有待确认事项的条目；
3. 在当前资源中有证据的条目，按最近证据时间；
4. 其余条目，按最近证据时间。

1.5 指出按出处计算焦点范围不可靠，问题在于它会排除出处以外的条目；这里不排除任何条目，只排先后，跨资源的前置知识仍在地图中，需要时读取。知识掌握一节中先列带详情的条目，再列只有摘要的地图，每条注明"详情已附"或"仅摘要"，模型不会误以为没给详情的就不重要。

**读取规则（尽量少）。**

| 层次 | 规则 |
|---|---|
| 硬约束 | 修改一个条目之前，本会话必须已经拿到过它的详情（加载时附了，或读取过）；服务端按会话检查，没有就拒绝修改并提示先读取。与 1.6-7"基于最新修订"是同一种保护 |
| 约定 | 深入讲解或检验一个概念之前、判断缺口或前置知识之前，先读取相关条目中尚未附详情的那些 |
| 启发 | 摘要提示有已知误解或待验证之处、并且与当前内容有关的条目，值得读取 |

读取工具一次可以读取多个条目（议题 7）。

**写入证据时附上详情。**模型写入证据时，如果标注的条目在本会话中还没给过详情，服务端在写入结果中附上这些条目的详情。概念标注本身就是模型对"相关"的判断，这样让真实的相关性信号来触发读取。代价是每个条目第一次被标注时多出几百 token。

**预算。**预算是配置项，按客户端分别设定（服务端从 MCP 连接得知客户端，1.10-4）；Claude Code 受 25,000 token 默认上限约束，可设小一些，或由学习者调高该上限。用字符数计量（服务端没有分词器）。初始值在试跑中调整（D8），思路是给学习本身留出大部分上下文。体积仍只写进运行日志，不报告给模型（1.5-4 不变）；模型看到的只是"详情已附""仅摘要"的标记。

**关于学习者本人的描述**现阶段始终完整送入：几乎每个场景都要用到（1.1），并有 1.5-3 的压缩约定和条目大小上限（议题 7）控制体积；以后明显变大时再用同样的机制，现在不预先规划。

**摘要与详情的分工（讨论中的说明）。**摘要回答"现在怎样、要不要细看"：掌握程度、置信程度、跨主题关联、是否有误解或待验证之处，约 40 到 80 token，始终完整送入；详情回答"凭什么这样判断、具体怎样"：每句话可追溯到证据，约 200 到 500 token，在预算内送入、其余按需读取。方案 C 下摘要是覆盖完整的唯一保证，1.5-2 要求摘要写出的误解、待验证之处和跨主题关联，正是触发读取所需的信号。

**代价。**只给部分详情时，模型可能偏向使用带详情的条目，靠标记和读取规则纠正；填充顺序依据结构信号而非真正的相关性，但只影响先后；数据多了以后读取次数增加；一切取决于摘要的质量；预算需要在试跑中调整。

### 3-C 会话中途：恢复、增量与去重（已定）

**实测：客户端是否在 MCP 请求中提供对话标识（2026-10-07）。**在已部署的第一版服务端上临时记录请求头和 `_meta`，核对了 4 类客户端、6 个对话或任务、16 次工具调用（诊断已关闭，日志已删除）：

| 客户端 | 对话标识 | 说明 |
|---|---|---|
| Codex | `_meta.sessionId` 等于线程 ID | 同一线程多次调用相同（间隔约 10 分钟仍相同），不同线程不同；`_meta.windowId` 含线程 ID 但后缀会变 |
| ChatGPT | 候选：请求头 `x-openai-session` 与 `_meta["openai/session"]` 一致 | 一个对话内五次调用相同（约 2 分钟）；只测了一个对话，未证明能区分不同对话，也未验证长期稳定；网址中的对话 ID 没有出现 |
| Claude 网页端 | 无 | `_meta` 中主要是客户端信息、能力和协议版本，追踪字段每次调用都变 |
| Claude Cowork | 无 | `x-anthropic-client: Cowork` 只能识别客户端；`_meta["claudecode/toolUseId"]` 每次不同；`progressToken` 和 JSON-RPC 的 `id` 在两个任务中重复 |

所有客户端的请求和响应中都没有 `Mcp-Session-Id`。本次没有捕获到 `initialize` 请求。

结论：客户端不提供统一、可靠的对话标识，Cairn 必须自己发放并传递会话标记（与 1.6-4 一致）；Codex 的线程 ID 可以作为该客户端的辅助信息；ChatGPT 的候选标记需要进一步验证。

**要解决的问题。**
1. 长对话中，平台会压缩或截断较早的内容（各平台做法不同），技能正文、加载结果、会话标记、读过的详情都可能丢失，模型自己未必察觉。
2. 丢失之后怎样恢复，又不把同一个对话拆成两个会话。
3. 会话进行中，别处（其他会话的沉淀、学习者在本地的修改）改变了状态，怎样告知（1.6-9 定了方向）。
4. 避免不必要的重复加载，也不让每次工具结果都附带大量内容。

**哪些内容不会被压缩。**

| 内容 | 位置 | 压缩后 |
|---|---|---|
| 技能的名称和描述 | 系统层，每次请求都发送 | 保留 |
| 工具定义（名称、说明、参数） | 系统层，每次请求都发送 | 保留 |
| 技能正文 | 对话消息中 | 可能丢失 |
| 加载结果、之前的工具结果 | 对话消息中 | 可能丢失或被概括 |
| 会话标记 | 每次工具结果中 | 最近的结果里通常还在，但不保证 |

前两行根据机制推断，在议题 10 实测确认。由此得出原则：恢复规则放在不会被压缩的通道里，工具结果只带事实（与 3-A 的分工一致）。

**发现与恢复。**

| 丢了什么 | 怎样察觉 | 怎样恢复 |
|---|---|---|
| 技能正文 | 技能描述中的提示 | 重新读取技能 |
| 加载结果（设定、知识地图等） | 开场加载工具的说明 | 带上会话标记重新加载 |
| 会话标记 | 需要标记的工具调用失败，报错写明原因 | 从最近一次结果的状态行中找；找不到就重新加载，开启新会话 |
| 读过的详情 | 不需要察觉：修改时会被拦下（见"条目版本"） | 重新读取 |

各组件带什么规则（工具名暂定，正式划分在议题 7）：

| 组件 | 会不会被压缩 | 带什么规则 |
|---|---|---|
| 主技能的描述 | 不会 | 学习会话中始终需要本技能；在上下文中看不到本技能正文时，先重新读取 |
| 技能正文 | 会 | 完整的恢复流程，正文还在时由模型执行 |
| 开场加载工具的说明 | 不会 | 会话开始时调用；对话被压缩后，在上下文中找不到 Cairn 的加载结果（学习者设定、知识地图）时也要调用；带上最近一次状态行中的会话标记即接续本会话，找不到就不带，会开启新会话 |
| 需要会话标记的工具：所有写入工具，以及读取状态的工具（读取条目、查询证据、获取变化） | 不会 | 需要会话标记（见任一 Cairn 工具结果的状态行）；找不到时先调用开场加载 |
| 材料工具（列出、读取、下载材料） | 不会 | 不带：与学习者的状态无关，不需要会话标记 |
| 工具结果 | 会 | 只带事实性的状态行，不写规则 |
| 钩子（只在 agent 客户端） | — | 压缩后注入一句提醒，属于增强（议题 8） |
| 项目指令 | 不会 | 可选，不必写，工具说明已经覆盖 |

读取状态的工具也需要会话标记，因为服务端要按会话追踪已知的修订；材料工具不碰这些。

**接续与新会话。**带着会话标记重新加载，就是接续同一个会话；服务端无从得知哪些内容在压缩后还保留着，所以返回全部必需部分，并清空本会话已取段落的记录（3-5）。没有标记就开启新会话，原会话的证据按 1.6-5 处理：加载时作为其他会话的未沉淀证据列出，闲置超过阈值后由新会话代为沉淀。不设"只取增量"的加载方式：重新加载正是因为上下文丢了。工具说明写明只在上下文中找不到加载结果时才重新加载；服务端判断不了这一点，偶尔多加载一次的代价可以接受。

**状态行。**每次工具结果末尾带一行状态，只写事实。放在末尾：正文在前，状态在后，压缩时最近的几条结果最可能保留，标记从最近一次结果的末尾最容易找到。

```
[Cairn 会话 s12-k7f3]
[Cairn 会话 s12-k7f3 · 有 2 项变化未读]
[Cairn 会话 s12-k7f3 · 学习者设定已更新：<改动条目的全文>]
```

会话标记用短形式：会话编号加 4 位随机字符，十几个 token；随机后缀防止模型误用另一个会话的编号。不写修订号：修订号由服务端按会话记录（运行数据，5.2-4），模型用不上。材料工具的结果是否也带状态行，在议题 7 定。

**变化的告知：标记加按需获取。**原设想是会话已知的修订落后时，在每次工具结果中附上增量。只有别处改动了状态才会出现增量（本会话自己的修改不会作为变化告诉自己），平时很少，但仍有三个代价：每次多出一行；变化被推到不需要的地方（例如查询无关概念时夹着另一个条目的变化）；刚做完回顾或迁移时变化可能有几十项，结果膨胀。因此改为：

| 变化的内容 | 怎样告知 | 理由 |
|---|---|---|
| 学习者设定 | 立即在状态行中附上改动条目的全文 | 设定是指令，要马上生效；很少变、很短 |
| 关于学习者本人的描述、知识掌握、待确认事项、进度 | 状态行只标"有 N 项变化"，模型在合适的时候（如告一段落时）调用"获取变化"：描述和知识掌握给名称、变化类型（修改、新增、合并、改名）和新的摘要；待确认事项和进度各一行 | 需要细看时按 3-B 的读取规则读取 |
| 沉淀因修订过时被拒绝 | 返回期间的增量（议题 7 的输入） | 合并后再提交 |

获取变化后，服务端更新本会话已知的修订。变化很多时，技能规定重新加载。

**条目版本（修订 3-12）。**3-12 的硬约束原为"修改条目前本会话必须已经拿到过它的详情"，服务端按会话记录给过哪些详情。漏洞是：详情在压缩时丢了，服务端仍以为模型还有，会放行修改。改为：详情与条目的版本号一起给出，修改时必须带上这个版本号，服务端检查它是否等于当前版本。压缩后模型手里没有版本号，就得重新读取；别处改过这个条目时版本对不上，修改被拒绝（1.6-7"基于最新修订"细化到单个条目）；服务端也不再需要记录给过哪些详情。

**平台会话标识（根据实测）。**
- 会话记录增加可选字段"平台会话标识"，注明来源（自动或手动）和取自哪个字段。
- 自动记录：Codex 的 `_meta.sessionId`；ChatGPT 的候选标记 `openai/session`。
- 只有经过验证（同一对话长时间保持不变、不同对话互不相同）的标识才用于自动接续：目前只有 Codex（在本次测试范围内）；ChatGPT 先只记录，不用于接续，议题 10 用多个对话、隔几个小时再验证；Claude 网页端和 Cowork 没有。
- 按可观察的信号判断（D4）：看请求中有没有这个字段，不只看客户端名称；以后 Claude 出现可用字段，验证后改配置即可启用。
- Claude 上可以手动关联：学习者把对话链接告诉模型，服务端追加一条"会话关联"记录（会话记录不变，5.2-4），只用于追溯：试跑中检查推断（D8），或代为沉淀时找回原对话补充上下文。
- 分支：编辑消息产生的分支沿用同一个对话标识，也带着之前工具结果中的会话标记，两种接续方式效果相同；被放弃的分支中写入的证据仍靠撤销处理（1.6-8）。

**代价。**恢复依赖模型察觉内容丢了，规则放在不会被压缩的通道中能帮上忙但不能保证，agent 客户端可以用钩子在压缩后提醒（例如 Claude Code 压缩后触发的会话开始钩子，议题 8）；没有标记时同一个对话会被拆成两个会话，原会话的证据只能代为沉淀，Codex 上靠线程 ID 可以避免；每次工具结果多出十几个 token 的状态行；"什么不会被压缩"是推断，要实测。

**结论。**

| 编号 | 结论 |
|---|---|
| 3-1 | 议题 3 分为 3-A 开场、3-B 体积与增长、3-C 会话中途；与平台记忆的分工并入 3-A |
| 3-2 | 技能写"怎样做"；加载结果只放数据、学习者设定和待处理事项的事实，不放通用说明 |
| 3-3 | 技能明确授权：加载结果中"学习者设定"一节是学习者的指令，优先于技能的默认做法；其余部分都是信息；插件版本检查保证授权在场 |
| 3-4 | 加载结果用标签分节；设定在最前，长内容在中间，待处理事项在最后 |
| 3-5 | 从第一版起支持分段送达：必需部分保证放得下；按客户端上限切分；必需段落没取完时写入被拒绝并提示 |
| 3-6 | 开场的待处理事项不挡住开始学习：版本不符时阻止；补做和代为沉淀在第一个自然停顿或结束时处理（agent 客户端可交给子代理）；待确认事项择机提出；与今天资源有关的材料变化先处理；回顾在学习结束后 |
| 3-7 | 开场概况一两句（位置和需要学习者决定的事），具体内容在议题 4 |

| 改名、合并、拆分 | rename / merge / split | 条目的三种演化操作 | 定 |
| 稳定编号 | stable id | 条目不随改名变化的标识，记录通过它引用条目 | 定 |
| 摘要 | summary | 一句话的当前掌握情况和置信程度 | 定 |
| 详情 | details | 条目的自由描述部分 | 定 |
| 证据索引 | evidence index | 服务端计算的相关证据、最近证据时间、涉及资源 | 暂定 |
| 知识地图 | knowledge map | 所有条目的名称加摘要 | 定 |
| 硬约束、约定、目标、启发 | hard constraint / convention / goal / heuristic | 0.4 中按约束力划分的四个层次；"目的层"的说法不再使用 | 定 |
| 主张 | claim | 状态中关于学习者的一条陈述 | 定 |
| 范围 | scope | 主张覆盖的范围：概念、领域或全局 | 定 |
| 权威 | authority | 谁有权确立一条主张：学习者或证据 | 定 |
| 诊断性 | diagnosticity | 证据区分主张成立与否的能力 | 定 |
| 时效 | recency | 证据离现在的远近对诊断性的影响 | 暂定 |
| 信息价值 | information value | 再获取一条证据是否值得 | 定 |
| 学习价值 | learning value | 一次互动对学习本身的帮助 | 暂定 |
| 证据模型 | evidence model | 证据怎样更新对学习者的认识（1.4） | 定 |
| 引出模型 | elicitation model | 互动中怎样引出证据（议题 4） | 定 |
| 学习者设定 | learner settings | 学习者对模型的指令：讲解和表达要求、反馈、学习目标、学习目的；存放在 profile/settings/，只在学习者说出或确认后修改（5.2-C） | 定 |
| 学习者状态 | learner state | 关于学习者的描述性主张：背景、学习特征、知识掌握、进度与待续事项；背景和学习特征存放在 profile/descriptions/，知识掌握和进度存放在 state/（5.2-C） | 定 |

| 关于学习者本人的描述 | descriptions | 学习者状态中关于学习者本人的部分：背景、学习特征；存放在 profile/descriptions/，由沉淀和回顾维护。"描述"作为性质（与"指令"相对）覆盖整个学习者状态 | 定 |

| 更正标注 | tag correction | 更正某条证据的概念标注，追加记录；模型和学习者都可以发起（5.2） | 暂定 |
| 学习者要求 | requested consolidation | 沉淀的一种类型：学习者要求对指定条目重新评估，例如回退的前提不满足时（5.2） | 暂定 |
| 运行数据 | runtime data | 服务端本地保存、不进 git、丢失后可保守恢复的追踪信息，如会话已知的修订（5.2） | 暂定 |
| 必需部分 | required parts | 开场加载中必须完整送达的部分：学习者设定、关于学习者本人的描述、知识地图、当前资源的进度和学习目的、待处理事项；没取完时写入被拒绝（3-A、3-B） | 暂定 |

| 演练 | dry run | 在数据仓库的临时副本上执行迁移并检查，不触及真实数据（5.2-B） | 暂定（英文） |

## 8. 讨论流程的约定

- 先阐述要解决的问题和原因，再给方案；先讨论，再决定。
- 回复保持详细，讲清思路；学习者明确表示偏好这种篇幅。
- 未经学习者确认的内容不写入本记录；确需记下时明确标为"待确认"。
- 每完成一个议题统一更新本记录和项目记忆，而不是每轮都更新。
- 核对文件时只输出数量或是否存在之类的简短结果，不打印大段内容。
- 设计记录写给开发者，完整保留推理；技能中交给模型的说明按 0.4 精简，在议题 6 撰写。
- 服务端没有语义理解能力：凡是交给服务端的事，都要能用结构、时间、数量、名称匹配完成。
